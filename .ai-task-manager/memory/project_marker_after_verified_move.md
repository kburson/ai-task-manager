Recurring defect (hit again 2026-07-08 on #737): `aitm-last-known-state state="review"` was stamped while the board card sat in `Develop`. The marker lied about a state the board never reached, producing a 2-hop split-brain that no sanctioned tool could clear (promote/demote drift-refuse; reconcile revert-to-recorded can't multi-hop; accept-live forbidden; direct move-state forbidden). Only a manual UI drag fixed it.

**Desired invariant (user directive):** never stamp `aitm-last-known-state` or the timing-log state-move row _before_ the board Status field is confirmed changed. Order must be: (1) issue the board move → (2) re-read the Status field and verify it equals the target → (3) only then stamp the marker + timing row. The marker becomes a record of a _verified fact_, never a _prediction_. Add a post-move verification guard so a silently-failed/reverted move can never leave the marker ahead of the board.

**Recovery trap (hit on #734, 2026-07-08):** when the board Status is BEHIND the marker chain (board=develop, markers already at review), do NOT "catch the board up" with `move-state --out-of-band develop→test→review`. Each out-of-band move stamps a fresh `aitm-entered-<stage>` marker, and since the chain's last state was already `review`, those register as illegal backward arcs (`review→test`) that the close-gate chain-audit rejects. The board field is stale but the markers are RIGHT — you need a board-field-only sync, not new transitions. Correct fix would be a marker-preserving board write (reconcile revert-to-recorded is meant for this but refuses multi-hop). Fallback that worked: out-of-band-move to catch up, then strip the spurious `aitm-entered-*` markers via `mutateIssueBody({allowMarkerLoss:true})`, then close. Also confirmed #748 Defect 2 live: close's move-state wrapper misread the `[human-reviewer-audit:info]` stderr line as a board-move failure and left the issue OPEN even though board→done + issue-close had already succeeded; a second idempotent `/task close` reported "already fully closed" but did NOT re-tick the two trailing lifecycle boxes ("Story closed…", "Timing data flushed") — had to tick them via `mutateIssueBody({allowUnverifiedTicks:true})` after verifying both facts true.
