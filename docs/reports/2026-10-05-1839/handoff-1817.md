## Matched workload

The frozen declaration selects exactly two launcher sessions in two linked worktrees sharing one scratch Git common root. The workload performs two repetitions per worktree, 30 minutes apart: sanctioned solo issue creation, bind, Refine entry, refinement completion into Ready for Planning, Plan entry and native stop. Four completed creation-to-planning workflows are the normalization denominator. Stop traffic is included in the interval's totals because it flushes the same workflow's timing and ownership; smoke, pilots and the aborted launch are excluded.

Keep the same shape, supported label, assignee ownership, priority p2, size S, estimate 1 hour, repeat rank, canonical eight-state Project semantics, recipe inputs, command order, start spacing, participant count, successful-workflow denominator and observation signal for a future comparison. The scratch repository and Project identifiers are runtime inputs; different expendable resources may reproduce the setup. Recompute recipe/configuration hashes and disclose differences rather than pretending new identifiers match the historical literal hashes. Allow for empty-board versus warmed-board behavior, field discovery, idempotence reads and concurrent updates.

The collector file hashes, version and source commit are frozen in `preflight.json`. The declaration was saved before enrollment and before the accepted interval. The worker supplied repository, issue/draft and lifecycle stage explicitly at each command boundary; stages describe the invoked workflow phase and are operator attribution, not independent board-state reads. Query fingerprints identify normalized query shapes without retaining literals or response payloads.

Native issue creation, comments, body edits and Project updates may involve hidden requests beyond one invocation.

An operation shape observed after freezing but absent from the pilot candidate groups remains visible in the raw report and operation breakdown. It is not added retrospectively to a declared group. ## Savings boundary and next comparison

There is no implemented #1817 optimization arm in this measurement, so no before/after or point-savings claim is supported. The known point subtotal is a lower bound from exposed same-response costs. Unknown costs and CLI-hidden requests prevent complete point prioritization even when invocation-volume coverage is sufficient. Account rate-limit samples are contextual shared-budget evidence; differences between those samples are not repository-attributable point costs.

For a future optimization arm, rerun the same controlled recipe in a newly configured disposable clone with fresh predeclared sessions and frozen operation groups. Report raw totals, completed workflow count, per-workflow normalization, timings, failure/denial/malformed coverage and changed configuration/version controls for both arms. Compare opaque volume only with opaque volume, and observable HTTP attempts only with observable HTTP attempts. A point-savings comparison needs complete comparable point evidence or an explicitly bounded subset; do not convert unknown costs into zero.

Collector process overlap and observed request activity are different measurements. The hour validates the declared collection interval; commands generate short bursts within it. Command duration sums can exceed elapsed wall time because the two worktrees overlap. This four-workflow sample is deliberately small and synthetic. It gives reproducible controlled evidence for planning, not a population estimate for everyday AITM usage.
