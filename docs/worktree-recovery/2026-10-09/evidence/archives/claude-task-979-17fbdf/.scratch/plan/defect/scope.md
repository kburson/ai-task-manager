Give the operator one generic, evidence-bearing escape hatch for delivery-invariant refusals, instead of adding a bespoke code branch per obscure failure mode.

Today AITM has exactly two shapes for a delivery requirement: a catalog item the operator can waive on the record via `workflow-exception`, or a hard `throw` with no lever at all. Every `delivery.*` requirement in `scripts/task-tracker/lib/workflow-policy/catalog.mjs` is hard-coded `waivable: false`, and several delivery predicates (merge-method among them) are bare throws inside `delivery-verification.mjs` that carry no catalog id, so no exception record could reach them even if the family were opened.

The consequence is that a small, benign, unforeseen divergence strands a delivered issue permanently. There is no supported way for a human to say "I have looked at this, I accept it, move on" and have that decision recorded as theirs.

In scope: make delivery invariants waivable-with-disclosure rather than plainly waivable, generalizing the pattern #1755 shipped for attribution. Route each delivery-verification refusal through an addressable catalog id; gate the waiver on a `workflow-exception` record carrying a substantive human reason and the exact scope; and make the resulting delivery receipt state which invariant was waived, by whom, and why. A waived delivery must never render as an ordinary pass.

Out of scope: a per-failure-mode reconciliation branch (explicitly rejected — that is the thing this issue exists to avoid); weakening or removing any delivery predicate; changing Full-Auto's authority, which is not and must not become a substitute for a human waiver; npm publication.

**Relationship to #1783.** #1783 asks for the same thing one tier narrower: a user-authorized, issue-scoped close authorization for the no-PR local-trunk lane, with hard constraints that are exactly right — fresh explicit user statement naming the issue, binding to one issue/repo/SHA/ref/expiry, refusal under unattended automation, a visible comment plus a typed marker, close output that distinguishes it from ordinary delivery, no project-wide config mutation, and no agent self-authorization. This issue proposes the generic mechanism that should satisfy #1783 rather than a second parallel backdoor: same authority model and same constraints, addressable across every delivery invariant instead of one lane. If that generalization is accepted, #1783 becomes a consumer of this mechanism rather than an independent implementation, and the two should not ship separate authorization paths.
