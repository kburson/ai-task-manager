## Blocking findings

### SAR-R1-F001 — P1 — Define active-plan authority and consumer selection

**Location:** Input draft lines 46–48 and 54–67.

The role set distinguishes source, accepted and decomposition plans but has no explicit active implementation-plan role or normative mapping of consumers to roles. A common resolver accepting a requested role cannot ensure callers select the same authority. Legacy aliases are required to match corresponding roles without those correspondences being defined.

**Failure scenario:** A child inherits parent plan A and its task selector, then acquires its own implementation plan B while accepted-plan names predecessor C. Current `linkedPlanReference` chooses Implementation-plan before Source-plan; `selectStoryIntentTask` explicitly refuses an inherited selector conflicting with the active plan. WBS intentionally reads Source-plan provenance. Implementers could map these consumers to different proposed roles, all through the common resolver, and change existing refusal semantics or inspect different bytes.

**Required change:** Define the role for a current draft implementation plan, exact legacy-field mappings, and a consumer selection table for roots, epics and children. Specify inherited-selector applicability and whether/how a child-owned plan changes active selection while preserving provenance. Retain existing explicit conflicts unless deliberately redesigned. Include an A/B/C fixture with distinct revisions. Byte equality alone must not erase different path/commit provenance when sharing entries.

### SAR-R1-F002 — P1 — Specify acceptance evidence and the producer contract

**Location:** Input draft lines 42–50, 79–85 and 105.

The draft requires authentic applicable evidence but does not define evidence variants or validation relationships permitting reviewed/accepted status. It leaves the standalone interface as either payload or manifest without selecting a common schema, acceptance subject, instance/round identity, or negotiation result. These choices determine authority.

**Failure scenario:** A committed manual SAR manifest says accepted and references predecessor response bytes; a standalone manifest supplies protocol acceptance. Both have valid digests. The specification does not define which evidence validates which subject, required sealed-protocol finalization, or handling of unknown assurance types. Separate repository implementations can adopt incompatible rules while satisfying the prose.

**Required change:** Select a versioned producer/consumer envelope with required fields/types, review-instance IDs, round/revision identities, acceptance subject, evidence-kind discriminator, lineage edges, and terminal/nonterminal semantics. Define manual SAR, sealed protocol and human acceptance validation. Unknown evidence may remain historical evidence but must not establish acceptance. Specify unavailable identity observations and deterministic capability negotiation/fallback. Include predecessor SPR/later XPR and unsupported-version examples. The standalone deliverable should implement this agreed contract rather than invent it later.

### SAR-R1-F003 — P1 — Fence stale publishers and state concurrency limits

**Location:** Input draft lines 91–105 and 115.

Normal publication checks ownership/current bytes but lacks an expected prior publication identity, monotonic cursor or record revision precondition. Local mutation locking is mentioned only for backheal. Current `upsertOwnedComment` updates after listing, identifies ownership by marker, and accepts no expected old digest.

**Failure scenario:** Publisher A publishes accepted round 3. Delayed publisher B holds an authentic published round-2 manifest, discovers A’s generated comment and overwrites it because there is no human modification. Both read-backs can succeed. Two remote creators can also observe absence and create duplicates; subsequent uniqueness refusal leaves duplicates behind.

**Required change:** Bind each effect to the expected prior publication identity/digest and a forward-only cursor. Define identical retry, stale request, divergent lineage and human-edit outcomes. Extend the governed writer’s preconditions and local serialization for normal publication. Explicitly document remaining cross-host/human races without server-side conditional writes; read-back alone cannot guarantee absolute no-overwrite or exactly-one publication. Specify conflict preservation/recovery and tests for delayed round 2 after round 3 and concurrent creation. If strict global serialization is required, identify its enforceable mechanism.

### SAR-R1-F004 — P1 — Define historical migration admission through session guards

**Location:** Input draft lines 109–121 and 26.

The design requires governed multi-issue historical changes without changing lifecycle/timing. It does not define admission through existing writer policy. `assertGovernedMutationSession` at `scripts/task-tracker/verbs/issue-body.mjs:239` requires the target to be the active issue with an open timing session; both body and comment verbs invoke it. A scope/proposal digest is not currently a recognized mutation capability.

**Failure scenario:** An operator authorizes migration of two closed stories while the migration implementation story is active. Both existing writers reject the targets. Implementation must start timing against historical stories, bypass the verb guards, or invent an exception. Those outcomes conflict with preservation requirements or leave a governance decision unspecified.

**Required change:** Design a narrow migration admission path: owning task/session, target scope, authenticated authorization receipt, proposal/backup binding, permitted effects, exact-ID retirement capability, revocation/expiration or consumption rules, and resume/rollback reuse. Preserve ordinary caller session guards. Define journal expected-state progression so verified migration effects become the next baseline without silently accepting unrelated drift. Test closed targets under another active issue, wrong/expired scope, partial resume and rollback authorization.
