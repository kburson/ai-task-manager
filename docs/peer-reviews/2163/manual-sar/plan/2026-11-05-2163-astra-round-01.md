## Required findings

### SAR-PLAN-R1-F001 — P1 — Define a child environment that preserves admission and isolates fixture identity

**Plan evidence:** Lines 63-67 define fixture actors, physical repositories, a provider executable and public Start, but do not define the subprocess environment that selects the actor, roots, offline mode and executable transport. Lines 17 and 67 require real admission, and lines 66/71 require no fallback network path. Those requirements are not established merely by placing a `gh` executable in a fixture directory.

**Source evidence:** `scripts/run-tests-pool.mjs:33-38` copies the parent environment and clears only project-root aliases; it intentionally preserves native identity and other context. `scripts/task-tracker/lib/verb-preflight.mjs:145-150` immediately returns a successful skipped-network preflight when `TT_SKIP_NETWORK=1`, before live-state and assignment evaluation. `scripts/task-tracker/lib/worktree-relocation-guard.mjs:148-152` also skips location enforcement under that flag. Meanwhile `scripts/gh/lib/gh-client.mjs:23-51` permits an explicitly declared offline `gh` double under the same flag. Thus a fixture can issue provider calls and reach the real verb while silently skipping the very admission paths this plan promises to exercise. Inherited root aliases also remain relevant to direct targeted runs, and inherited host actor/capture/lock/provider settings are not made fixture-owned merely by the `actor` option.

The existing local fixtures illustrate why this must be intentional: `location-authority-fixture.mjs:66-92` clears network-skip, project aliases, injected session/transcript settings and credentials, while the native-bootstrap fixture constructs a restricted environment and fixture home (`native-worktree-bootstrap.test.mjs:67-113`). Neither fixture can be copied wholesale because this plan also prohibits their unrelated substitutions and requires its own actor definitions.

**Required change:** Add a concrete environment contract to fixture construction and `run`: fixture-owned home/config/transcript and actor identity; no ambient project-root, inherited lock, capture/evidence, provider-session or executable-injection authority; real Git/Node paths; a child-local provider path whose resolved `gh` is verified as the fixture executable; and admission enabled with `TT_SKIP_NETWORK` absent or `0`, with no configuration escape such as disabled assignee gating. Explicitly distinguish the trusted bootstrap environment from the provider-run environment. Specify how an absent or displaced provider executable fails before the CLI can reach the real network while admission remains enabled. Do not use `TT_SKIP_NETWORK=1` as the network-isolation solution for these public runs.

**Validation:** Add a fixture launch test with a deliberately polluted parent environment containing network-skip, foreign roots/actor IDs and an inherited transport/capture setting. Prove that the child uses only the fixture environment, produces actual assignment/location/preflight requests and Start state, and cannot reach real `gh`. Removing or moving the declared provider must refuse before any provider/business write. Retain the sanitized child environment manifest or a nonsecret identity projection with the evidence. This can be implemented entirely in fixture code; no production admission relaxation is requested.

### SAR-PLAN-R1-F002 — P1 — The promised unrelated contributing-comment drift barrier is not supplied by the planned changes

**Plan evidence:** Line 99 explicitly adds drift in **other contributing comment bytes**, between invocations, and requires the named refusal with zero unauthorized next write. Lines 90/93/94 only calculate the new operation's mapped-target digest, preserve the prior-intent derivation short circuit, and recheck the target audit comment. No step defines how unrelated source drift is checked before a pending retry persists or applies effects.

**Source evidence:** On a matching pending retry, `estimate-writer-publication.mjs:363-369` uses the sealed `prior.intendedInputDigest` without calling derivation. Its saved before-record check validates the sealed record and adapter identities (`:370-452`), and its business checkpoint reads only registered effect targets (`:453-466`). The publication owner context includes subject, scope, kind and policy, not the complete forecast/comment observation (`decomposition-projection.mjs:201-211`). A resuming pending manifest is checked for sealed-manifest equality instead of comparing the current full input against the original digest (`:451-459`). Metadata persistence checks current availability/context and confirmed effect readbacks; its fresh-base check compares two current reads, not either read with the original unrelated comment bytes (`:491-539`, `:543-619`). The final full-input comparison occurs after the business-effect loop (`decomposition-publication.mjs:159-165`).

**Concrete static counterexample:** Start a candidate operation with the refine comment plus a separate valid HUMAN ATTENTION proposal comment. Interrupt before the audit write after the before-record is durable. Between invocations append harmless bytes to the separate proposal comment, leaving its parsed hours/size, target audit comment, issue scope, policy and all effect values unchanged. The production collector remains available but its forecast source digest changes. The planned target correlation still passes and new derivation is suppressed by the matching prior. Existing checkpoints do not reject that other comment before the retry can persist metadata and apply the remaining audit/field effects. The final collector can then report drift, which is weaker than the specified no-next-write outcome. This is a source-grounded static trace, not a claimed executed reproduction.

**Required change:** Add an explicit bounded validation design and implementation step for non-effect contributing authority on pending retries, before the first resumed publication persistence and business effect. Identify the retained immutable expectation and how the current observation is compared while accounting only for already authorized audit/field transitions. The check must preserve the sealed intended digest, retain the real collector, and must not accept the final observed digest as replacement authority. Explain how this validation coexists with the requirement that the original intended-input derivation remains short-circuited on retries. If the intended scope instead permits effects after this particular source drift, that is a specification-contract change requiring a separate disposition and review, not a green test achieved by redefining or dropping the case.

**Validation:** Use the transport-only public fixture to retain a real pending operation, mutate the bytes of a separate contributing comment without changing its parsed proposal fields, and retry identical argv. Assert a specific source-drift refusal before any new metadata or business write, exact preservation of the sealed intent and audit bytes, and the full ledger boundary. Include the clean identical retry alongside it to show that allowed in-progress audit/field values are still resumable. Do not choose only the already-completed repeat path, where the existing completed-authority check would mask the missing pending-retry guard.

### SAR-PLAN-R1-F003 — P2 — Separate an unpersisted first attempt from a sealed retry in the fault oracle

**Plan evidence:** Line 97 applies interruption/lost-response tests to the initial metadata boundary and uniformly requires the original operation/time/intent to be retained. The fault inventory at line 122 explicitly includes a fault **before** each physical write. This includes failure before the first publication marker has ever reached provider state.

**Source evidence:** `executeEstimateWriter` selects the time from `prior.createdAt` only when a matching publication exists, otherwise from the current clock (`estimate-writer-publication.mjs:272-310`). The accepted specification and plan line 93 preserve that design. The first publication is persisted at `decomposition-publication.mjs:111-113`; the versioned writer awaits the provider write at `versioned-issue-write.mjs:406-409`, with a pre-application transport failure propagating before any durable marker exists. If the provider never applied this first write, the retry has no persisted creation timestamp or sealed intended digest to recover. Across midnight its newly prepared audit can legitimately differ. Keeping the abandoned in-memory time would require an additional durable mechanism that the plan does not provide and the accepted scope does not require.

**Required change:** Split the fault matrix by durable outcome. Before any intent write was applied, assert no publication/business effects and treat the next invocation as a new preparation against unchanged authority; preserve deterministic operation-key behavior where applicable, but do not require an unpersisted creation time or audit digest to survive. Once an intent write may have landed, first read actual provider state: if a matching prior is present, require its exact operation/time/intent and audit bytes; if absent, apply the new-preparation case. Keep all before/after fault cases and explicitly preserve the stronger invariants for genuinely sealed retries. No new journal or timestamp override is requested.

**Validation:** Add paired deterministic unit cases crossing midnight: first-write rejection before application with no prior record, and response loss after initial intent application with the record present. The former may choose the later creation time; the latter must retain the earlier sealed time and intended bytes. Public cases must classify their persisted outcome from real provider state rather than assume every failed invocation left a prior manifest.

This is materially significant: two actual verification groups meet `reviewVerificationGroups: 2` and produce a decomposition-review signal (`:15-22`, `:159-167`); a hidden zero count would omit that signal. No dynamic parser execution was performed in this read-only review.

**Required change:** Express each task's verification commands using the existing recognized whole-line `Run:` form or proper command fences, keeping explanatory prose outside the declarations. Add an explicit preapproval step to inspect the real parsed task/verification-group counts and handle the resulting native decomposition review normally. Do not change the parser or conceal one task's commands to preserve a smaller signal count. Distinguish the intentional original RED command from the candidate verification command without making either invisible to source analysis.

**Validation:** The revised exact plan must parse as two tasks with the expected nonempty command lists and two verification groups. The supported native explanation/Plan checks must retain and disposition any resulting `needs-decomposition-review` signal before Develop. Record actual native output; a manually asserted count is not equivalent evidence.
