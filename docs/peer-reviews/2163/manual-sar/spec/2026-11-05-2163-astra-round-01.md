## Review reasoning

### Exact authority and predictive intended input

The failure hypothesis is supported by the local production source. The verb prepares and patches the whole refine comment (`inflate-estimate.mjs:243-290`). The production proposal collector hashes the complete raw comment and identifies a Planned Estimate using the GraphQL comment ID (`decomposition-authority.mjs:317-431`). The generic intended-input calculation clones the forecast observation but only updates projected field values (`estimate-writer-publication.mjs:55-105`). Final publication compares the real newly collected input digest against the previously sealed intended digest (`decomposition-publication.mjs:159-169`). This explains the proposed own-audit mismatch without establishing that the required registered-entry reproduction has already occurred.

The specification predicts only the prepared audit's exact digest change. It requires each actually contributing initial proposal from the mapped GraphQL comment to have the before-body digest, replaces only that digest in a clone, preserves other proposals and observations, recomputes the complete forecast observation digest, and applies the existing intended projection. It neither substitutes a final observed digest nor changes generic hashing, retirement, owner admission or final collection. A comment with no actual initial contribution does not create a synthetic observation. These boundaries preserve the distinction between calculated intent and observed authority.

### Provider identity and completeness

The proposed numeric REST ID plus opaque node ID correspondence is realistic for the current code: both initial and later-page projection queries already request GraphQL `id`, `databaseId`, `body` and issue containment (`estimation/runtime-adapter.mjs:133-164`). `loadForecastProjection` exposes a transport callback and follows its real pagination and record parsing (`:324-367`, `:401-461`), so the verb can observe raw comment nodes without replacing the authoritative forecast reader.

The spec correctly adds explicit shape, same-issue/repository, duplicate-identity, unique dual-domain mapping and exact-body checks. It does not use equal text as identity. Its strict transport-reader requirement matters because the present REST reader discards malformed pages (`inflate-estimate.mjs:138-162`), while the projection pagination and record parser are not themselves a substitute for validating every ordinary comment's required correlation fields. The required first-page/later-page checks and incomplete/error/duplicate-page refusals close that design gap. The explicit recheck against the freshly read audit source, followed by existing input/effect checkpoints, avoids treating an earlier mapping as a write authorization.

### Parser semantics and injected content

The chosen comparison uses the actual proposal parser on both complete bodies and requires availability plus equal semantic proposal fields other than source digest. Keeping a fixed comparison context with retirement and published-forecast suppression disabled is necessary: the production parser can otherwise retire a valid Planned Estimate at `decomposition-authority.mjs:398-422`, making an empty-to-empty comparison conceal a semantic change.

The spec separately preserves actual contribution from the authoritative initial forecast; the comparison context does not become collection authority. Full-prefix retention and package-prepared append bytes constrain what can change. Required refusal cases include changed Planned Estimate fields, duplicate headings, added/removed proposals, ambiguous Markdown and injected operation markers; legitimate earlier audits remain supported. This is a sufficient specification contract. The concrete plan must implement those checks rather than assume that one parser equality assertion alone detects every marker ambiguity.
