**SAR-1901-R2-01 — P2 — Preserve durable queue checkpoint semantics separately from remote publication acknowledgment**

Specification references: lines 109 and 182.

Line 109 preserves existing journal checkpoint ordering and runtime authority. Line 182 now says publication “commits its checkpoint only after correlated read-back.” In context, this is canonical remote read-back. That changes the existing durable queue contract: a successfully queued immutable row currently permits its local checkpoint to advance even though remote publication remains pending.

Current evidence:

- `scripts/task-tracker/lib/actor-flush-journal.mjs:164–176` explicitly distinguishes durable queued bytes from confirmed remote publication, accepts either `ok: true` or `queued: true`, then commits the checkpoint and retires the journal.
- `scripts/task-tracker/runtime.mjs:499–527` implements that checkpoint by advancing the original actor’s word cursor and state.
- `scripts/task-tracker/lib/timing-post-outcome.mjs:3–17` supplies the queued result after a failed remote attempt is durably enqueued.
- `scripts/task-tracker/queue.mjs:71–79` persists the queued event; lines 102–115 retain failed deliveries for retry.
- The same queue module, lines 118–139, already distinguishes the stricter terminal requirement: pending timing must be remotely delivered before immutable outcome evidence can freeze.

The new wording leaves implementers choosing between incompatible requirements. Enforcing remote read-back before every checkpoint would block the existing offline progression and require additional coordination between the retained journal and queue. Keeping current code would violate the new normative sentence. Neither change is necessary to establish event-derived durations or replay-safe projections.

Proposed correction:

Replace the unconditional remote-read-back rule with an explicit two-path contract:

1. **Confirmed remote publication:** acknowledge source admission and the current valid projection after correlated canonical read-back.
2. **Durable queue acceptance:** preserve the existing local checkpoint progression once the exact immutable payload is durably queued. Report pending remote publication; queue delivery later performs source-identity reconciliation and canonical read-back before acknowledging/removing that delivery.

If neither remote publication nor durable queue acceptance succeeds, leave the checkpoint unchanged and retain recoverable journal evidence. Preserve existing stricter terminal/outcome gates; durable queue acceptance must never be presented as remote publication.

Add focused acceptance cases for failed remote publication followed by durable enqueue, checkpoint advancement without interval/word recount on the next flush, restart after queue acceptance, queue-write failure leaving the checkpoint unchanged, and subsequent delivery after projection reallocation.
