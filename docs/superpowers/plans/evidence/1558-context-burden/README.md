The V2 research supports the replacement plan's emphasis on complete workflow traffic, instruction reloads and compaction. It is **not yet a reliable quantitative baseline**, a verified set of complete workflows, or evidence of savings. The strongest verified contribution is a concrete post-compaction reload sequence that the current extractor accidentally discards.

## What is useful

V2 replaces the misleading whole-corpus/per-Done-task division with event records, explicit issue-attribution methods, raw character/byte counts, output locators and uncertainty labels. It also exposes real historical behavior that can guide representative fixture selection. These are useful methodological improvements even though the aggregate tables need repair.

## Corrections needed before quantitative use

| Finding                                                 | Evidence in the archived extractor                                                                                                                                                                                                                                                                               | Consequence and correction                                                                                                                                                                                                                                                                                                                  |
| ------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Content identity is being mistaken for event identity   | `addEvent` hashes provider/session/category/input/output; the final `seen` pass omits call ID, timestamp and segment from duplicate identity.                                                                                                                                                                    | Distinct repeated reads disappear. Deduplicate proven copies of the same event using provider event/call identity and import provenance. Retain distinct calls even when their contents are identical. Keep identical-content classification as a separate dimension.                                                                       |
| Compaction totals collapse repeated boundaries          | Compaction rows have empty input/output and the same category within a session. The ledger has 201 Codex reset rows at distinct source lines/timestamps, but the unique-content table retains only 29. Claude has 2,018 candidate hook rows reduced to 50.                                                       | These tables count unique content, not reset events. Codex's 201 rows corroborate the counting defect; Claude's hook rows need Pre/Post pairing and event-identity validation before inferring the number of resets. Do not simply promote 2,018 to a corrected reset count.                                                                |
| Close success is too permissive                         | `closeOutcome` accepts `Timing data flushed`, `Final Review Passed`, or generic `Done`/`closed`; it does not exclude truncated output. Isolated checks classify both timing-only output and `Done` followed by a truncation notice as successful close.                                                          | Require matching issue/action and definitive success evidence from the command's actual result, with explicit failure/truncation handling. Otherwise keep outcome unknown. A successful close alone also does not establish a fully observed bind-to-close workflow.                                                                        |
| Scenario labels exceed the selection evidence           | `compactionPool` tests only multiple session/segment identities plus instruction reads; `heavy` selects maximum total event/character count. Scenario JSON contains aggregate issue records, not an ordered event-ID sequence. `compactionReloads` also includes initial segments and is silently sliced to 200. | Select a verified reset → instruction-load → next-action chain; distinguish fresh sessions, initial loading and true resets. Prove the heavy scenario's refusals/remediations. Include ordered locators and selection rationale, with any output cap disclosed. All current candidates are Claude; add separately justified Codex coverage. |
| Context categories are not yet specific enough          | `workflowTerms` includes `scripts/gh`, `guard-registry` and `lifecycle`. A synthetic ordinary code search `rg -n guard-registry scripts/tests/unit` is classified as help/discovery. A compound tool call is assigned to the first recognized fragment while all output is counted in that bucket.               | Separate product development/debugging from requests for workflow guidance. Preserve mixed-call output as mixed/unknown unless it can be partitioned from actual subcall outputs. Do not claim the full help or host-instruction bucket is reducible by #1558.                                                                              |
| Cohort completeness and attribution need outcome checks | Active binding is updated from the attempted command before its result; issue groups are keyed by provider/issue. Distributions pool providers and observation classes; the completed label requires only any successful-close classification.                                                                   | Do not change active binding after a failed bind. Distinguish provider/issue observations from repository-unique issues; stratify by provider, work type and actual coverage. A partial log with a close is still a partial workflow.                                                                                                       |
| Character accounting differs from the plan's proxy      | The extractor uses `[...text].length` (Unicode code points), while the plan's established proxy uses JavaScript `text.length` (UTF-16 code units).                                                                                                                                                               | Retain UTF-8 bytes and raw text identity; state units and use the plan's convention for comparable proxy results. Historical returned content, current file sizes and tokenizer counts remain distinct measurements.                                                                                                                        |

The table identifies reproducible algorithm defects and bounded counterexamples. It is not a claim that every classified event is wrong, nor a corrected re-estimation of the entire corpus. No new savings percentage or population average is inferred here.

## Follow-up for the research agent

Repair event-identity deduplication first, then rerun attribution, close classification, compaction pairing and cohort/scenario selection; all downstream totals depend on those steps. Add regression cases for the three actual reload pairs above, two distinct compactions in one session, a duplicate import of one event, failed bind followed by an unattributed read, timing-only/truncated close output, a multi-session issue with no reset, and an ordinary lifecycle-code search.

Publish a new version rather than overwrite this reviewed snapshot. Supply distributions by provider and actual observation completeness, complete ordered scenario locators, and explicit unknowns. The original extraction script hard-codes its workspace and log roots; a rerun should parameterize those paths and record the exact invocation/source identities. Do not claim that a fixed cutoff alone makes malformed or timestamp-less records reproducible, since its `beforeCutoff` currently admits those records.

Acceptance-quality context savings still require the plan's paired execution and tokenizer calibration. The research can support scenario selection and explain the burden; it cannot establish the replacement's effectiveness on its own.
