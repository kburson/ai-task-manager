## Summary

I checked the spec's source claims against the tree at the recorded artifact
commit and they hold. `normalization.mjs::requireReady` maps every non-ready
decision to `normalization-authority-drift` (lines 16-28). `review.mjs:1484`
only destructures `scanBody`/`persisted` from `deriveAndRescan` and throws away
`decision`. `close.mjs:3644-3646` throws drift for known unchecked/lifecycle
prechecks. `mutateIssueBody` refuses ticks without proof (#362) and refuses newly
introduced proof unless `evidenceStamp` is set (#522). The direction is sound:
a separate, typed reviewed-evidence family that never counts as execution proof,
and carrying original blocked decisions through to their own renderers instead
of hiding them behind drift.

The spec isn't ready yet. Two design gaps can leave issues permanently blocked.
First, the new "checked Scope item needs evidence" rule is applied to existing
legacy bodies, which today can legitimately carry proofless Scope ticks, and
the spec gives no compatibility boundary (R1-F001). Second, history is
append-only, every new HEAD requires a fresh record, pruning is forbidden, and
the GitHub body size is fixed, so an issue can run out of space and have no way
to recover (R1-F002). Two eligibility and binding rules are also left vague
enough that the implementation plan would have to make security-relevant
choices the spec should make (R1-F003, R1-F004).

## Findings

### R1-F001 — The new checked-Scope evidence requirement breaks existing legitimately ticked Scope items, with no compatibility boundary

The spec says (Transaction and readiness): "checked narrative Scope items must
have either their established valid execution-proof route or valid reviewed
evidence ... Unchecked eligible Scope items and checked items missing both forms
of evidence also block. Run this validation independently of the accepted-Test
early return in the legacy completeness guard." It also says: "No auto-migration
asserting that inspection happened."

Today's behavior is different:

- `test-exit-pre-close-completeness-guard.mjs:25` returns `ok` as soon as there
  is accepted Test evidence. Otherwise it only refuses *unchecked* items
  (`uncheckedPreCloseCheckboxes`). Nothing checks whether a checked Scope item
  has proof.
- `check.mjs::classifyUnverifiedTick` (lines 181-197) returns `eligible` for any
  line that isn't Functional DoD, a verifier-bearing AC, or an undeclared AC
  line. So a narrative Scope item can be ticked today through the sanctioned
  `--allow-unverified-ticks` hatch, which leaves an audit marker but no
  execution proof.
- Scope boxes ticked in the GitHub web UI, or before #362, also carry no proof.

Failure scenario: an in-flight legacy issue (not generated by split-plan) has a
hand-written `## Scope` checklist whose items were ticked with the honest hatch
during Develop. Its accepted exact-SHA Test receipt exists. Under this spec,
Test→Review now blocks on every one of those items. The guard no longer
short-circuits on accepted Test, and hatch audit markers are neither execution
proof nor reviewed evidence. The only way forward is to re-record reviewed
evidence for each line on the current HEAD. That may be impossible when the
original attachments are gone, and it turns a historical honest-hatch decision
into a gate failure. The spec covers "legacy/directory lane routing" but doesn't
say which *legacy* bodies the new checked-item requirement applies to.

### R1-F002 — Append-only history with a full record per entry, per-HEAD invalidation and no pruning can exhaust the issue body and leave the issue permanently blocked

The spec persists "the complete canonical validated record" in a same-line
encoded comment. It requires "A new HEAD requires a new validated request". It
appends a superseding record rather than replacing the old one, and it states
"Refuse history/body-size limits before writes; never prune history to fit."
GitHub issue bodies have a fixed upper bound of about 65,536 characters, and the
body also has to hold ACs, DoD, timing/rollup markers, the deep dive and Plan
Metadata.

Failure scenario: the six-step child from the reported #132 case. Each record
holds binding (repo, issue, worktree path, branch, 40-hex HEAD), provenance,
rationale, an artifact path and digest list, actor, timestamp, the
preceding-record digest and the lineage id, then gets encoded. That is plausibly
1-3 KB per record. Each Develop fix commit or rebase after recording changes HEAD
and stales all six heads. After enough cycles the next recording hits the size
refusal. From then on the issue can never get a valid current head, so
Test→Review blocks forever. The spec forbids the only in-body remedy (pruning)
and offers no other one. "Refuse before writes" makes the failure explicit, but
it doesn't make it recoverable.

### R1-F003 — "Scope lines declaring machine verifiers are ineligible" has no detection rule

Eligibility is the safety boundary between reviewed judgment and machine proof,
but the spec never says what counts as "declaring a machine verifier" on a Scope
line. The codebase has several verifier shapes: `aitm-verified cmd="…"`,
`aitm-verified-by`, vc-list citations (`vc:N`), and execution-proof
`ts`/`sha`/`evidence` markers already on the line. `classifyUnverifiedTick` only
handles the AC-section forms through `findEvidenceAc`.

Failure scenario: a Scope line cites `vc:3` (or carries `aitm-verified-by`)
without an inline `cmd=`. If the implementer reads "declares a machine verifier"
as "has `cmd=`", that line becomes eligible for reviewed inspection evidence. A
demonstrable step then gets satisfied by operator judgment instead of running
its verifier, which is exactly the authority expansion the spec says it rejects.
The misplaced-marker refusal and the AC2 "verifier-bearing Scope targets" case
can't be tested consistently without a defined predicate.

### R1-F004 — Live worktree/branch/HEAD binding at Test→Review readiness doesn't say where readiness has to run

The record binds a canonical worktree, branch and full HEAD, and "Only the
current head must match live binding ... at ... Test-to-Review readiness."
`deriveAndRescan` reads HEAD with `git rev-parse HEAD` in the process cwd
(`review-derive-rescan.mjs:29`). Test-stage execution in this project runs in an
isolated sandbox worktree (Develop-Phase Verification Contract; Test-stage CI
emulation). The spec doesn't say whether readiness has to be evaluated from the
bound operator worktree, how a sandbox worktree is treated (different path,
possibly detached HEAD), or how attachments are expected to persist. They're
most likely gitignored files under `.scratch/`, which is the case the spec
mentions only as "Ignored attachments become unavailable on another worktree".

Failure scenario: the operator records evidence in their Develop/Test worktree,
and `/task review` or `promote` then runs from the main checkout or another
linked worktree at the same SHA. The worktree path doesn't match, so every
reviewed record reads as stale and Test→Review blocks. The diagnostic suggests
re-recording, which binds to the new path and stales the old checkout's view. Or
the implementer quietly loosens the worktree comparison. Either way the
behavior is decided by the plan, not the spec.

## Required changes

1. Resolve R1-F001. Define exactly which bodies the new checked-Scope evidence
   requirement applies to. For example: only bodies carrying a split-plan
   generation marker or a new body-version threshold, with all other legacy
   bodies keeping today's unchecked-only semantics and accepted-Test
   short-circuit. Separately, state how existing honest-hatch audit-marked Scope
   ticks are treated (accepted as the legacy route, or explicitly refused with a
   named recovery), and how proofless web-UI ticks are treated. Add fixtures for
   each: legacy hatch-ticked Scope with accepted Test, legacy web-UI-ticked
   Scope, and generated child Scope under the new rule.
2. Resolve R1-F002. Either give a recovery path that keeps the issue recordable
   once the size limit is reached, or bound growth by design. Options: compact
   superseded records into digest-only chain stubs while the current head keeps
   the full record, which preserves chain integrity without the full historical
   payload; or store full records in a durable issue comment or receipt store
   referenced by digest from the line. Include a worked size estimate for the
   six-step case across N HEAD refreshes, and say what operator action is
   available when the limit is reached.
3. Resolve R1-F003. Name the exact markers and citation forms that make a Scope
   line verifier-bearing. At minimum: `aitm-verified cmd=`, `aitm-verified-by`,
   vc-list/`vc:N` citations, and existing execution-proof markers. Require one
   shared pure predicate used by the writer, the proof guard and the readiness
   validator, and cite it in the AC2 cases.
4. Resolve R1-F004. State where Test→Review readiness must be evaluated relative
   to the bound worktree. Define worktree identity (canonical realpath; whether
   a different linked worktree at the same branch and HEAD matches). Say how
   sandbox and detached-HEAD Test worktrees are handled, and where attachments
   are expected to live so they survive until readiness. Add a fixture for
   readiness invoked from a non-bound checkout.

## Optional suggestions

1. Every commit after recording stales every Scope record. Consider saying
   outright that operators should record reviewed evidence after the final
   Develop commit, ideally in Test where code writes are already refused, so
   people don't churn evidence and history (which also eases R1-F002).
2. The target-content hash excludes only the glyph and reviewed-history markers.
   State whether other same-line markers added later by sanctioned writers
   (hatch audit markers, timing or derived markers) stale the record or are also
   excluded. Otherwise an unrelated sanctioned write could silently stale
   evidence.
3. In the AC3 row, name the Review renderer that will consume the preserved
   decision. `review.mjs:1484` currently drops `decision`, so the plan needs a
   concrete seam to change, not just the normalization layer.
