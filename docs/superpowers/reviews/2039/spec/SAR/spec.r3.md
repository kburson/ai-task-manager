## Intent and required outcome

Owners must be able to estimate from local evidence without exhausting the shared GitHub allowance on historical discovery. Disabling the rubric must stop estimation before indirect network work. The assigned agent accumulates story-body, comment and timing changes in project-local `.tmp/gh`; it publishes a single batch at each governed state transition after comparing the cached revision vector with a bounded current cloud snapshot. Detected drift produces a retained diff for user discussion and merge, not an overwrite or automatic rebase.

Success requires zero cloud backlog/history/calibration reads in every estimation mode, explicit disabled or unavailable results, bounded target publication traffic, and retained evidence for conflicts and uncertain writes. Preserve lifecycle, assignee, ownership, decomposition, proof, timing and Unknown semantics. Local estimates and cached observations are evidence, never permission to skip safeguards.

This changes estimation input, story caching and state-transition publication interfaces. Implementation and its detailed execution plan are later stages. The owner's later instructions supersede the initial issue's arithmetic body-version rule and this draft's earlier per-effect publication design: use native per-resource revisions plus exact current-content hashes, a dirty manifest, all current comments, and state-transition batching. The intermediate local-greater-version-wins proposal is superseded; no integer comparison grants overwrite authority. The [SAR scope-change record](../reviews/2039/spec/SAR/scope-change.md) preserves that sequence without changing the live issue or checking acceptance criteria.

## Approach selection

1. **Selected: local calculation plus cached state-transition publication.** Remove network capabilities from calculation; accumulate owned changes locally and retain native guards at admission and transition boundaries.
2. **Read coalescing alone.** Improves amplification but retains prohibited corpus discovery and optional baseline enforcement. Insufficient.
3. **Global network/CLI disable.** Stops traffic but blocks authorized issue updates and leaves the architecture broken. Insufficient.

## Estimation boundary

Introduce a pure mode resolver before estimation transport construction, estimation authority collection and estimate-specific preflight. Hooks run in separate processes before the CLI: each supported command hook must independently use the same local mode resolver and canonical command classifier before constructing its estimation/decomposition query; a check only inside the verb runner is insufficient. Rubric ID `0` means disabled; a positive safe integer means local. Missing effective configuration, negative, noninteger, unsafe-integer or malformed configuration means unavailable/config-invalid. The existing configuration default of `0` remains disabled; distinguish an intentionally defaulted value from a parse failure. Never normalize invalid configuration into enabled mode.

Calculation receives immutable local inputs and pure functions. It has no GraphQL/REST client, `gh` executor, comment store or lazy network loader. Return a discriminated result:

- `disabled`, reason `rubric-disabled`: no inferred estimate, calibration, bootstrap publication or automatic forecast write.
- `unavailable`, with concrete missing/invalid input reasons: no generated estimate or new estimate-publication intent.
- `estimated`, containing size/hours, input digest, model/policy identity and reproducible local provenance.

Disabled mode stops automatic estimation. Explicit human estimates remain eligible for the governed manual/compatibility path with human attribution; that path stages owned changes locally for the next transition without enabling rubric loading. Preserve existing estimates. Disabled/unavailable never means zero hours, erased values or a fabricated forecast-ready marker. Update CLI rendering and exit handling for these results. An explicit estimate-generation request returns a distinguishable non-success exit for disabled/unavailable and stages no inferred estimate. Successful estimate generation stages a proposal; it does not flush the cloud. Compound Refine/Plan commands may continue only independently authorized human-input or lifecycle work whose native gates pass; report calculation and publication/admission outcomes separately. Preserve the existing disabled-rubric manual approval route; enabled mode with missing local evidence cannot impersonate disabled mode to bypass forecast requirements.

Local inputs comprise the selected plan at its recorded commit/digest, retained Refine values, supplied evidence, retained rubric and retained outcomes. Validate repository identity, schema, lineage, hashes, plan identity and timing completeness. Keep missing durations Unknown. Rubric-based calculation requires a valid local rubric; no cloud fallback or guessed bootstrap estimate. Comparable evidence may be empty only if the existing model explicitly supports it and records that limitation.

Use a versioned local evidence bundle/index under native durable runtime storage, resolved through existing root/storage identity APIs. Populate it from verified records already observed during ordinary issue work or explicit local file import. Import is offline, validates provenance and grants no lifecycle authority. Cache misses, invalid selected-plan evidence or unsupported schemas return unavailable. No automatic cloud hydration, scheduled warmup or relocated backlog scan.

### Local evidence contract

Define `aitm.local-estimation-evidence/v1` as a manifest over immutable, content-addressed payloads. Required fields bind GitHub host and canonical repository; subject issue; effective rubric configuration; selected plan path, section, commit and content digest; retained Refine size/hours and source identity/digest; model/policy version; an ordered rubric/outcome input list; and each input's record ID, schema, payload digest, lineage, provenance and observation/import time. Digest canonical JSON using SHA-256 with a named canonicalization version. Missing or conflicting required fields refuse the whole calculation; timestamps do not establish freshness or authority by themselves.

Retain existing AITM record envelopes and their exact payloads for observed/imported rubric and outcome records, including predecessor/supersession chains. Reject duplicate IDs with different bytes, ambiguous active branches, missing required ancestors, wrong repository/host, invalid hashes and unsupported schemas. Pure refresh may derive a new local rubric with a stable valid record ID, predecessor and payload hash; persist it before forecasts reference it. Reuse the existing rubric and outcome semantic validators. Preserve the half-hour forecast grid and distinguish incomplete/Unknown timing from measured zero. No local record is presented as a verified GitHub comment: source kind is explicitly `observed-cloud`, `imported-local` or `derived-local`, with a source comment identity only for actually observed comments. Imports establish declared provenance and structural integrity, not external attestation.

Current forecast v2 accepts a rubric record ID but has no local-input provenance field. Introduce a versioned successor forecast schema for newly published local forecasts, carrying the evidence-manifest digest and a self-contained immutable provenance snapshot sufficient to interpret rubric identity/version, selected plan, Refine source and selected outcome identities/digests without cloud dereferencing. Preserve legacy v1/v2 reads for existing records; update all new-write validators, approval/exit consumers, renderers and outcome correlation together. Never fabricate a cloud rubric record or rewrite legacy records merely to satisfy the new schema. Full local input payloads remain retained for replay; the published snapshot identifies them and their origin, without publishing unnecessary historical bodies. If local payloads are lost, replay is unavailable rather than silently hydrated from the cloud.

Remove project corpus loading from all calculation/calibration chains. Preserve cloud readers only if non-estimation consumers still require them, with tests proving they are unreachable from estimation or evidence refresh. Rubric refresh consumes validated local outcomes and records its result locally.

## Native revision evidence and authority

The owner-authorized [native revision probe](../reviews/2039/native-revisions/2026-10-19-native-revision-probe.md) supplies the provider evidence. Unedited issue bodies and comments returned no edit node and `lastEditedAt:null`. Real edits changed the tested latest edit ID; an identical-content update left it unchanged. After a first edit the connection count included creation, so it was two while the UI said one edit. The controlled comment returned the latest edit with `first:1`, while `last:1` returned creation. Never use a count, timestamp order alone or arithmetic on opaque IDs as a cloud version.

Deleting the diagnostic comment's older B revision retained its ID and a deletion tombstone while current C content, latest C ID, count and timestamps stayed unchanged. Native current-content metadata does not detect historical redaction. Cache current body/comments only, not edit-history diffs; do not resurrect redacted history or use it as estimation evidence. Latest-edit deletion, issue-body-history deletion, comment deletion, alternate permissions and concurrent writes were not experimentally verified. Unknown/deleted latest-history authority must not silently select an older surviving edit. Preserve the current-content observation and require reconciliation when the revision shape is unsupported.

Define each cached resource observation as host/repository/issue identity, resource kind and node ID, exact current UTF-8 body and SHA-256 digest, observation time, and native revision metadata. A complete unedited response is an explicit `unedited` mode with no edit ID; edited mode retains latest edit ID, edited timestamp and deletion indicator plus `lastEditedAt`. Provider errors, missing fields, partial connections and inaccessible nodes are `unavailable`, never an empty/unedited resource. Timestamps are provenance, not standalone concurrency tokens. Validate the latest-node timestamp against the returned latest-edit metadata; an inconsistent/unsupported shape is unavailable. Compare the supported revision mode/tuple and exact content digest, not `updatedAt` alone or history counts. Explicit reconciliation may establish a supported content-digest observation when native history is unavailable but complete current content and identity are independently readable; it must record the limitation and cannot silently downgrade an existing native-token conflict.

The manifest is a vector of body and comment observations plus the complete current-comment inventory. There is no native aggregate story revision. Save node IDs for direct read-back and recovery; also take a bounded issue-scoped inventory at each transition to detect new/deleted comments. Equal total counts do not prove equal inventories. Compare all cached current resources, including read-only external comments; an added, removed or changed block is drift to show the user. Do not enumerate the project or unrelated issues.

The tested GraphQL issue/comment mutation inputs have no expected-edit-ID argument. A snapshot comparison followed by ordinary writes is optimistic conflict detection, not atomic compare-and-swap. An external user, bot or other machine may edit after validation, and successful read-back cannot prove no intervening content was overwritten. Assignment does not lock GitHub's editor. This remaining race is disclosed, not represented as owner-approved atomic safety. No provider guarantee beyond the probe is claimed.

## Project-local cache, manifest and writer ownership

Resolve the actual consumer project/worktree root using native root identity APIs, then place the cache below that root's `.tmp/gh`, never the AITM package installation directory. Each issue cache contains immutable current-cloud baseline body/comment payloads, separate working payloads, a manifest, native pending timing events, and the publication/recovery journal. Manifest identity binds host, canonical repository, issue node/number, project/item, owning human, owning session and worktree. Resource entries bind node ID, baseline revision/digest, working digest, ownership classification and `clean`, `dirty`, `conflict`, `dispatching`, `uncertain` or `confirmed` outcome. Store with atomic local replacement and user-only permissions; corrupt/incomplete identity or failed required persistence refuses publication.

Cache every current target-issue comment. Foreign/user-authored comments are read-only cached context; ownership requires an established native record identity and sanctioned writer capability, not merely a recognizable heading or the assignee's login. The timing log retains its stable canonical comment node ID and all historical multi-actor rows. New owned comments carry local intent identity before they have a provider node ID. No custom cloud metadata comment is needed merely to count versions; a record with a genuine native approval/publication purpose remains a separately accounted resource.

Every authorized local body/comment change atomically updates working content, its digest and a local dirty tag; the manifest is dirty if any owned resource or timing event is pending. No metadata read, body write, comment append or timer projection is dispatched for those tiny edits. Baseline bytes and native tokens remain immutable during the pending batch. Local reads display working content as unpublished and identify the last observed cloud baseline; status/Explain show dirty/conflict/uncertain state. Remote consumers can see only last-published content and cannot infer that another machine has no unpublished work.

Allocate a publication generation and unique batch ID exactly once when a transition freezes its batch. These identify local recovery only; they are not invented GitHub edit IDs and never authorize overwrite. Freeze the working digests, transition identity, resource effect manifest, approval/proof references and native timer cursor boundary. Subsequent edits are blocked or placed in a distinct next pending generation; they cannot change an in-flight candidate. Confirmed read-backs advance only the corresponding resource baseline, with the original batch baseline retained in the journal. The aggregate dirty/incomplete state clears only when every required effect and the final transition completion are verified.

Require exactly one live assigned human equal to the authenticated writer when acquiring ownership and at every transition flush, including early states. Separately require one persistent owning agent session/worktree for the issue cache. Existing `ownershipDecision` admits team-unassigned early work and same-login sessions; add a cache-writer-specific gate instead of globally changing read-only/team semantics. Use a shared repository-scoped ownership registry to record the unique session/worktree/cache path and claim identity, with a short-lived native issue lock for acquisition, handoff and flush. The registry is an ownership pointer, not a second body/timing authority. A second session under the same login must refuse; expiry or a crashed process never silently discards or steals unpublished work. Native local edit hooks validate this claim without network. Assignment changes made remotely between boundaries are discovered at the next boundary and block publication.

Handoff, reassignment, worktree removal and runtime cleanup must settle, explicitly transfer or export the entire pending cache/journal before releasing ownership. Protect dirty/conflict/uncertain entries from ordinary `.tmp` cleanup; they are not regenerable caches. A handoff transfers exact bytes, native baselines, event cursors and journal under the shared claim, verifies their hashes and names the new owner. If a cache is lost or unavailable, refuse and surface the missing unpublished evidence; no backup survival after arbitrary `.tmp` deletion or worktree destruction is claimed. Clean caches may be refreshed only with no unresolved intent. `.tmp/gh` is the owner's selected storage location; do not duplicate authority in a different durable store.

Initial cache acquisition performs one bounded targeted hydration of the issue and all current comments plus required ownership metadata. It does not scan history or the backlog. Any incomplete census, duplicate canonical timing log, conflicting record identity or unreadable block makes the required cache unavailable. Record which resources are genuinely absent. An unedited body/comment is valid under the native contract; it needs no fabricated numeric marker or cloud initialization edit. Preserve existing legacy AITM body-version markers as historical compatibility data where required, but stop stamping/incrementing them as publication authority. Inventory and migrate readers that assume that marker controls writes.

## Timing accumulation and other comments

The native local timer remains the event source. Starting, resuming, pausing, ending a work interval, reporting and local timing projections append/consume local events into the cached timing working copy without individual cloud writes. Preserve event IDs, actor attribution, transition IDs, ordering, actual timestamps, persisted cursors, measured durations and Unknown semantics. Replaying an event is a deterministic no-op; do not generate extra rows/durations to compensate for an uncertain write. Preserve historical actors' rows while only the current authorized session generates new issue events.

At a transition, freeze the local timing cursor and render one composite timing-log candidate containing all unpublished events and the legitimate phase-exit/entry pair. The pair uses one native transition identity and actual event time. It is published at most once, then verified by node ID, exact returned content and native metadata. Native timing records staged before final transition completion are provisional: consumers must correlate the transition ID with the final committed body sentinel before treating a transition row as completed lifecycle authority. Previously completed timing history remains intact; incomplete/unknown evidence never becomes zero or a completed visit by inference.

`gh-timing-comment.mjs` (`postTimingEvent`, `updateTimingComment`, `readCanonicalTimingSource`), `log-issue-time.mjs`, timer flushers, board rollup projections and `move-state/audit-timing.mjs` must route into this batch. Remove direct fallback body writes, per-row cloud append/re-merge/retry and side-write paths that would evade it. Verify every supported CLI/packaged/hook entrypoint. A routine timing command outside a transition only stages; it does not secretly turn into a flush.

The same resource batching applies to owned forecast/evidence/audit comments: coalesce allowed changes to one existing comment into one update per batch; distinct immutable record creations remain distinct effects. Preserve append-only record semantics rather than rewriting immutable envelopes to reduce calls. External comments are never rewritten, merged into the body or deleted by batching. New timing/comment creation is a separate operation with a stable local creation intent and resource-purpose key. A complete preflight inventory must prove the canonical resource absent; a timed-out creation is uncertain and must be reconciled against a bounded inventory before any further creation. Correlation IDs do not provide server-side exactly-once creation. Duplicate or ambiguous matches refuse and retain evidence.

## State-transition publication and native gates

The only routine automatic upsert event is a governed state transition along `Backlog → Refine → Ready for Planning → Plan → Develop → Test → Review → Done`, including supported demotions and existing governed special transitions. Use existing stage verbs and their guards; do not expose direct arbitrary state movement. End-turn, ordinary command completion, estimate generation and timing checkpoints do not flush. A same-state no-op is not a new flush; resuming an incomplete transition is recovery of its original batch. No additional explicit-save feature is introduced here.

Map the actual CLI, preflight and hooks before implementation, including `task-tracker.mjs`, `verb-preflight.mjs`, `activity-guard.mjs`, `source-edit-gate.mjs` and `decomposition-hook-authority.mjs`. Resolve estimation mode locally before estimate-specific network dispatch in every process. Scope cache allowances to recognized operations; disabling the rubric never exempts unrelated code edits, commits or lifecycle admission from native guards. Do not use `TT_SKIP_NETWORK`, remove telemetry or treat cached observations as fresh cloud authority.

Calculation remains local-only. Outside a transition, owned story-body/comment/timing writers operate on the pending cache; native governance reads for independently requested actions remain explicit and bounded, never hidden calibration or child scans. At transition, one bounded observation phase includes current body, all current comments and their native metadata/content, current assignment, configured project status/fields and needed governance metadata. Share those observations across compatible native guards and composite validation; no repeated body-version read for each marker, timing row or effect. Foreign ownership, state drift, inventory/revision/hash mismatch, missing data or incomplete pagination refuses before the first mutation and saves baseline/local/cloud diffs for discussion.

Estimate-only commands never traverse a child graph. A genuine lifecycle transition still enforces existing fresh child/dependency/decomposition gates when required; those reads belong to separately measured transition admission, are bounded, and may not feed estimation/history calibration. Do not move a prohibited estimation scan into a transition hook. If a required gate cannot obtain legitimate complete authority within its declared admission budget, refuse the transition rather than weakening the gate.

Use the pending candidate for native checks that legitimately validate the owner's staged plan/body changes, with retained approval/proof capabilities bound to the exact candidate scope and source evidence. Revalidate reviewed-scope, proof provenance, marker preservation, section-loss, timing and lifecycle conditions for the composite transaction, not merely each tiny patch in isolation. Any later local edit invalidates approval that no longer covers its scope. A local proposed approval marker is never evidence that an external approval happened. Where a gate specifically requires a verified cloud authority record before Status, publish/verify that required owned record within the transition batch and run the gate against that real result before Status. The later implementation plan must enumerate these cases and every validator/consumer changed; it cannot bypass them with a general 'batch mode' flag.

### Transition saga with one final body write

Current `move-state-core.mjs` writes timing and entry body evidence before Status, then a separate move-complete body sentinel after Status; `github-mutation.mjs` can compensate with another body write. That ordering cannot meet this requirement unchanged. Replace it with one explicit recoverable saga, including `transition-commit.mjs`, `sentinel.mjs`, readout, preflight and post-commit-tail consumers:

1. Acquire the persistent writer claim and native short-lived issue lock; recover any prior incomplete batch. Freeze one batch with baseline vector, full candidate body/comments/timing, native transition identity, required effects and source/target states. Persist all candidate bytes and event cursors in `.tmp/gh` before dispatch.
2. Obtain the single bounded current snapshot and complete inventory. Compare every baseline resource's identity/native revision/digest and current ownership/status. Run all pure/native pretransition checks available at this phase. On any drift or unverifiable authority, perform zero mutations, retain a three-way diff and return `conflict`/`unavailable` for user discussion. Do not automatically adopt cloud changes, bump a generation to evade conflict, or use the earlier greater-version-wins rule.
3. Apply each required non-body resource at most once in dependency order, coalescing the timing log into one upsert. Verify each mutation using its returned payload when complete or one targeted read-back. Publish any genuinely required pre-Status authority record and validate its result before Status. Journal each resource separately. The timing transition pair may be present but remains provisional until the final body sentinel commits that transition. Do not repeat the body snapshot before each comment/field write.
4. Apply/verify Status and any other required configured project fields using their native expected-value/ownership rules. Use one mutation per changed field/API resource, or a provider-supported combined operation only where its semantics are verified. Status confirmation is mandatory; the existing blind whole-write retry loop must not replay an uncertain mutation. A partially moved board is reported as pending, not completed.
5. After all required timing/comment/board effects are confirmed, materialize the final composite body from the frozen candidate with actual confirmed record IDs, entry/last-known-state/proof markers and the matching completion sentinel. Candidate validation may account only for these declared substitutions; recheck all body invariants and proof scope. Write the body once and verify exact returned content/native metadata. Never fabricate a completed sentinel before prerequisite resources are confirmed. Use only the existing documented trailing-whitespace transport normalization for candidate-versus-read-back comparison; store exact returned bytes/digest afterward.
6. Atomically checkpoint each confirmed resource and the final batch result; clear only the frozen pending events/edits that were confirmed. Report transition completion only when the body sentinel, required records/timing and board all agree on the same transition and the local journal commit succeeds. Subsequent edits remain dirty. Post-commit tails cannot cause another body/timing flush; required effects are included before finalization and optional follow-on work is reported/staged distinctly.

No intermediate cloud body stamp, body rollback or compensating overwrite is permitted merely to make the old saga appear atomic. A failure after some comments/Status changed leaves an explicit partial transition with the original frozen intent, baseline vector and per-resource results. AITM admission/readout must recognize the pending transition and block further lifecycle work; board/body mismatch must not be silently treated as a completed move or automatically repaired as a human move. Other machines lacking the journal fail closed on incomplete/mismatched cloud authority and require explicit handoff/reconciliation.

Recovery reuses the same batch and inspects only uncertain resources plus necessary current ownership/authority. It never reruns confirmed writes or invents new timing events. Exact intended content and consistent resource/transition identity can confirm an uncertain landed effect without another mutation; different content produces a diff/conflict. A single unchanged-baseline read does not prove a delayed request cannot land, so no automatic replay follows. Explicit user reconciliation decides a safe resume/merge and revalidates remaining effects. The original batch's one-attempt resource allowance is retained; a user-authorized replacement intent is recorded separately, not disguised as a retry or automatic increment. Failed local confirmation persistence also requires recovery before further writes.

Body and comment writes remain separate non-atomic provider mutations. The compare/write race covers the time spent on other saga resources as well; this design deliberately does not reinsert per-tiny-effect body verification. Read-backs detect some races, not every lost update. If a final verification observes changed required resources, preserve confirmed outcomes and refuse completion. Reconciliation never automatically overwrites or deletes newer remote content to roll back the saga.

## Conflict, reconciliation and retention

A conflict package stores the frozen baseline, working candidate, newly observed cloud current content/native metadata, complete inventory changes, human-readable three-way diff, batch/resource identities and all dispatch outcomes. Mark the manifest conflicted and leave dirty content available. Discuss the diff with the user before merging; equality of opaque native IDs is not enough if hashes differ, and a numerically 'larger' local generation is irrelevant. User-directed merge creates explicitly reviewed working content and a new accepted baseline; validate proofs/scope and current authority again at the resumed transition. Do not silently overwrite the baseline while pending intent exists.

A resource confirmed before another resource conflicts stays recorded as confirmed; do not clear the aggregate dirty/pending marker or resend it. Preserve old and new observations needed to distinguish landed from unlanded effects. Atomic local generations or a recoverable write-ahead commit record must prevent baseline/journal disagreement after a crash. Test persistence failure, partial files, nested locks, process restart, lost worktree and owner handoff. The cache remains in `.tmp/gh`; export is an explicit recovery/handoff action, not an unsolicited second authority store.

## Operation budgets and evidence

Budgets count actual attempted remote operations across hooks, CLI and spawned transports, including errors, verification and recovery. Keep operation counts separate from same-response returned GraphQL points. Unknown cost remains unknown; opaque CLI/browser layers are identified and overlapping collector views are not summed. No live expensive estimation replay or quota polling is required.

The zero-call contracts are hard: local calculation/rubric refresh and already-hydrated local body/comment/timing edits dispatch zero remote operations. Increasing pending body edits or timer events from 1 to 1,000 does not increase transition snapshot or mutation counts for the same resulting resource set. One body resource is written at most once; the timing-log resource is written at most once; each other owned dirty block/field has at most one manifested mutation attempt. Unchanged/external comments have zero writes.

Freeze the expected resource manifest independently of observed traffic. Let `S` be the fixed number of bounded snapshot pages/batches needed for the fixture, `G` its declared native admission operations, `D` its declared dirty/created body/comment/field resources, `V` any declared final convergence observations not already satisfied by effect read-backs, and `U` its uncertain-resource recovery allowance. The normal ceiling is `S + G + 2D + V`: at most one write and one read-back per declared resource; a complete mutation response may reduce the reads.
