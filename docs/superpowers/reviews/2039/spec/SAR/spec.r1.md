## Intent and required outcome

Owners must be able to estimate from local evidence without exhausting the shared GitHub allowance on historical discovery. Disabling the rubric must stop estimation before indirect network work. AITM may still publish authorized changes to the current issue, provided it compares the cloud body with its retained baseline, refuses drift, and verifies the result before advancing local authority.

Success requires zero cloud backlog/history/calibration reads in every estimation mode, explicit disabled or unavailable results, bounded target publication traffic, and retained evidence for conflicts and uncertain writes. Preserve lifecycle, assignee, ownership, decomposition, proof, timing and Unknown semantics. Local estimates and cached observations are evidence, never permission to skip safeguards.

This changes estimation input and publication interfaces. The owner requested a specification; implementation and its detailed execution plan are later stages.

## Approach selection

1. **Recommended: local calculation plus guarded target publication.** Remove network capabilities from calculation; retain guards through narrower observations and explicit unavailable outcomes.
2. **Read coalescing alone.** Improves amplification but retains prohibited corpus discovery and optional baseline enforcement. Insufficient.
3. **Global network/CLI disable.** Stops traffic but blocks authorized issue updates and leaves the architecture broken. Insufficient.

## Estimation boundary

Introduce a pure mode resolver before estimation transport construction, estimation authority collection and estimate-specific preflight. Hooks run in separate processes before the CLI: each supported command hook must independently use the same local mode resolver and canonical command classifier before constructing its estimation/decomposition query; a check only inside the verb runner is insufficient. Rubric ID `0` means disabled; a positive safe integer means local. Missing effective configuration, negative, noninteger, unsafe-integer or malformed configuration means unavailable/config-invalid. The existing configuration default of `0` remains disabled; distinguish an intentionally defaulted value from a parse failure. Never normalize invalid configuration into enabled mode.

Calculation receives immutable local inputs and pure functions. It has no GraphQL/REST client, `gh` executor, comment store or lazy network loader. Return a discriminated result:

- `disabled`, reason `rubric-disabled`: no inferred estimate, calibration, bootstrap publication or automatic forecast write.
- `unavailable`, with concrete missing/invalid input reasons: no generated estimate or partial publication.
- `estimated`, containing size/hours, input digest, model/policy identity and reproducible local provenance.

Disabled mode stops automatic estimation. Explicit human estimates remain eligible for the existing governed manual/compatibility publication path with human attribution, without enabling rubric loading. Preserve existing estimates. Disabled/unavailable never means zero hours, erased values or a fabricated forecast-ready marker. Update CLI rendering and exit handling for these results. An explicit estimate-generation request returns a distinguishable non-success exit for disabled/unavailable and performs no automatic publication. Compound Refine/Plan commands may continue only independently authorized human-input or lifecycle work whose native gates pass; report calculation and publication/admission outcomes separately. Preserve the existing disabled-rubric manual approval route; enabled mode with missing local evidence cannot impersonate disabled mode to bypass forecast requirements.

Local inputs comprise the selected plan at its recorded commit/digest, retained Refine values, supplied evidence, retained rubric and retained outcomes. Validate repository identity, schema, lineage, hashes, plan identity and timing completeness. Keep missing durations Unknown. Rubric-based calculation requires a valid local rubric; no cloud fallback or guessed bootstrap estimate. Comparable evidence may be empty only if the existing model explicitly supports it and records that limitation.

Use a versioned local evidence bundle/index under native durable runtime storage, resolved through existing root/storage identity APIs. Populate it from verified records already observed during ordinary issue work or explicit local file import. Import is offline, validates provenance and grants no lifecycle authority. Cache misses, invalid selected-plan evidence or unsupported schemas return unavailable. No automatic cloud hydration, scheduled warmup or relocated backlog scan.

### Local evidence contract

Define `aitm.local-estimation-evidence/v1` as a manifest over immutable, content-addressed payloads. Required fields bind GitHub host and canonical repository; subject issue; effective rubric configuration; selected plan path, section, commit and content digest; retained Refine size/hours and source identity/digest; model/policy version; an ordered rubric/outcome input list; and each input's record ID, schema, payload digest, lineage, provenance and observation/import time. Digest canonical JSON using SHA-256 with a named canonicalization version. Missing or conflicting required fields refuse the whole calculation; timestamps do not establish freshness or authority by themselves.

Retain existing AITM record envelopes and their exact payloads for observed/imported rubric and outcome records, including predecessor/supersession chains. Reject duplicate IDs with different bytes, ambiguous active branches, missing required ancestors, wrong repository/host, invalid hashes and unsupported schemas. Pure refresh may derive a new local rubric with a stable valid record ID, predecessor and payload hash; persist it before forecasts reference it. Reuse the existing rubric and outcome semantic validators. Preserve the half-hour forecast grid and distinguish incomplete/Unknown timing from measured zero. No local record is presented as a verified GitHub comment: source kind is explicitly `observed-cloud`, `imported-local` or `derived-local`, with a source comment identity only for actually observed comments. Imports establish declared provenance and structural integrity, not external attestation.

Current forecast v2 accepts a rubric record ID but has no local-input provenance field. Introduce a versioned successor forecast schema for newly published local forecasts, carrying the evidence-manifest digest and a self-contained immutable provenance snapshot sufficient to interpret rubric identity/version, selected plan, Refine source and selected outcome identities/digests without cloud dereferencing. Preserve legacy v1/v2 reads for existing records; update all new-write validators, approval/exit consumers, renderers and outcome correlation together. Never fabricate a cloud rubric record or rewrite legacy records merely to satisfy the new schema. Full local input payloads remain retained for replay; the published snapshot identifies them and their origin, without publishing unnecessary historical bodies. If local payloads are lost, replay is unavailable rather than silently hydrated from the cloud.

Remove project corpus loading from all calculation/calibration chains. Preserve cloud readers only if non-estimation consumers still require them, with tests proving they are unreachable from estimation or evidence refresh. Rubric refresh consumes validated local outcomes and records its result locally.

## Durable baseline and intent journal

Add a versioned issue-body baseline store and mutation-intent journal through native durable runtime storage resolution. Records survive restart and worktree replacement. Share per-repository/issue records across linked worktrees under a cross-process claim. Recovery evidence must not live only in purgeable `.tmp/aitm`. Register ownership and retention with runtime storage machinery. Use the existing issue-lock/record-claim ownership mechanisms as the outer serialization boundary, anchored to the canonical shared repository root; nested body/effect writers reuse a validated held claim rather than acquiring a competing lock. Define and test one acquisition order if a separate store lock is unavoidable, including same-process siblings, nested writers and spawned children. An environment flag alone cannot authorize an unrelated writer. Retain unresolved intents and every payload referenced by them; garbage collection must never discard recovery evidence or an input still referenced by a retained forecast. Keys include canonical repository, GitHub host and issue; project effects additionally bind project/item identities. Reject ambiguity.

A baseline contains schema, identity, exact returned body, explicitly present body version, digest, observation time and available provider metadata. Missing/invalid markers are unverifiable, never trusted version zero. Reject duplicate/malformed markers and unsafe integers, and refuse a mutation when incrementing the version would exceed the safe integer range. Keep legacy parsing for unaffected readers; use strict parsing for authority. Compare digests and versions: human edits may leave AITM's marker unchanged. Timestamps/ETags supplement evidence and are not presumed CAS tokens.

An intent contains operation ID, target, baseline generation/version/digest, declarative mutation description/patch, intended body/digest, relevant guard/input digests, timestamps and effect outcomes. Persist before the first write with atomic replacement and user-only access. Retain complete proposed bytes or a replayable patch; do not serialize executable closures. Failed persistence/corruption refuses mutation. The lifecycle is `prepared` (candidate and inputs durable), `dispatching` (persisted before transport), then `confirmed`, `conflict`, `not-observed` or `uncertain`. A restart seeing `dispatching` treats it as uncertain. Store the baseline and intent confirmation in one atomically replaced per-issue state generation, or use a write-ahead commit record that makes partial multi-file updates recoverable; independent renames of two files are not an atomic commit. Flush the file and directory as supported before acknowledging durability, preserve the previous valid generation, and refuse on unsupported/failed required durability. Record the supported crash/power-loss guarantees in implementation evidence.

A normal target read may seed an absent baseline before intent construction. Mutation without a valid baseline refuses `baseline-unavailable`; fetching a new baseline cannot silently legitimize an old intent. Drift retains the old intent and new observation, marks reconciliation required and prohibits automatic baseline adoption/retry. Explicit targeted reconciliation establishes a new baseline generation and reviewed/recomputed intent through governed interfaces. Ordinary reads may record newer observations but must not replace an existing authority baseline behind an unresolved or prepared intent. An absent baseline may be seeded only from a complete, strictly versioned target observation before creating a new intent. Missing/invalid cloud markers remain unavailable, including on legacy issues; this story adds no automatic marker repair or fabricated version-zero migration.

### Body write protocol

1. Acquire/reuse the repository/issue claim; load the retained baseline and recover unresolved intents before preparing another mutation. Validate native gates and calculation-input correlation.
2. Derive the candidate from that baseline; run existing mutation, marker, proof, section-loss and reviewed-scope guards; stamp the next version. Persist the complete `prepared` intent before prewrite validation so failed reads and drift retain the proposal. Persisting a candidate grants no permission to dispatch it.
3. Immediately before the effect, fetch the target body. Require matching identity, strict version and digest. Missing, failed, incomplete or unequal observations refuse before writing and record the failure/conflict. The read may serve same-phase consumers; old admission observations cannot substitute. If validation of fresh resource/guard inputs is asynchronous, perform it before this final body comparison or repeat the comparison afterward within the declared budget.
4. A no-op verifies/refreshes the same baseline without pushing or bumping. Otherwise persist `dispatching`, push once, then read the same target back. Require strict version and full body equality using only the existing trailing-whitespace transport normalization. Keep exact returned bytes/digest in the baseline; do not normalize interior content or relax the prewrite digest equality.
5. Atomically commit the verified returned body/version/digest and confirmed intent outcome. Expose success only after cloud confirmation and local persistence. Later effects use this new generation.

Route `mutateIssueBody`, direct `versionedWriteBody` calls and supported body adapters through this mandatory boundary. Derive expected version from the baseline; no optional production bypass. Tests may inject an in-memory store. Keep one lower-level implementation. Inventory direct issue-body CLI/GraphQL writers and route each through it or document a creation-only exception. New issue creation is a separate protocol, not mutation with fabricated version zero.

### Conflict, uncertainty and concurrency

Remove automatic rebase/retry on changed cloud bodies, including disjoint edits. Return typed conflict and preserve intent/evidence for explicit reconciliation. Preserve already committed effects; never roll back by overwriting newer cloud content.

A timeout or failed postwrite verification may mean a write landed. Record uncertain and allow one bounded target recovery read, without blind replay. Exact intended body/version confirms the effect; unchanged baseline means not observed as landed and requires explicit validated retry; different content means conflict. Failed recovery reads leave uncertainty. Cloud success plus local persistence failure means recovery required, not clean success. Restart reconciles before another write. Operation IDs and resource checks prevent duplicate owned comment/forecast effects only when their observations are complete and unambiguous. An ambiguous dispatch is never automatically replayed, including after a single recovery read still shows the baseline: a delayed request may land later. Explicit retry must acknowledge that uncertainty, establish fresh authority and recompute/revalidate intent; the operation ID is a correlation key, not a claimed provider idempotency token.

A local claim serializes cooperating processes sharing this store, not GitHub users, bots, other machines or independent stores. Separate compare/write leaves a time-of-check/time-of-use window: an edit after validation can still be overwritten even when later read-back matches. Read-back detects some races but cannot establish that no intervening edit occurred. **This is optimistic conflict detection, not atomic compare-and-swap or an absolute no-overwrite guarantee.** Owner acceptance must acknowledge this limitation or require a provider-supported atomic primitive. Do not assume REST conditional writes or GraphQL offer one without verified provider evidence and a design revision.

Comments/project fields are separate resources; body version does not version them. Revalidate the target body before each actual cloud mutation, plus each resource's native ownership/predecessor/expected-value checks and read-back. Persist an effect intent before dispatch for comments/project fields too, recording the target node/item, before-value digest, proposed bytes/value, ownership/predecessor and expected result. A non-body effect's read-back must also observe that the body still matches the baseline; combine body/resource verification where possible, otherwise count both reads. Any body drift prevents subsequent effects and success/convergence claims while preserving the already observed resource outcome. Never adopt that changed body automatically. Journal partial outcomes using the existing publication protocol. Never present this as a transaction across body, comments and project fields.

## Publication reads, budgets and freshness

Replace full-authority effect readers with resource-specific target reads: body for before-records, configured item fields for project effects, owned comments for forecasts. Reconcile predecessors from one observation per unchanged resource phase. Share projection promises within a phase; invalidate after corresponding writes, failed reads, conflict, restart or drift. Never reuse prewrite validation across mutations or make cached admission evidence indefinitely fresh.

Attribute attempts/completions/failures to operation, phase, purpose, resource and target. Count operations separately from returned GraphQL points. Keep HTTP/CLI coverage, unknown costs and opaque subprocess observations visible. Never sum overlapping collector views as independent cost or treat missing cost as zero.

These are proposed offline acceptance ceilings, not measured improvements. Freeze each fixture's effect manifest before executing its first mutation: enumerate every business effect, before-value marker, checkpoint/publication marker and finalization write with resource identity and allowed dispatch count. Let `M` be that independently reviewed maximum mutation count, not a count derived from observed traffic. The six-effect example below is illustrative, not a claim that today's epic publisher has six effects.

Count actual journal effects, not just business effects. Fit existing guards into the declared budget or seek design review before raising it. No-op/conflict ceilings apply to the body writer, not unrelated command setup.

First pages count toward the 10-page cap; `P` counts only allowed continuation operations beyond first observations already charged elsewhere. Bound a single response/stream to 4 MiB as well. GitHub comment connections may return unrelated comments on the target issue: parse them only to identify owned estimation records and completeness, never as historical calibration inputs, and never mutate unowned comments. Refuse before fetching page 11; stop on a response that crosses the byte bound and refuse mutation from incomplete observations. Require sequential pagination so parallel dispatch cannot exceed the page cap. These ceilings deliberately trade availability for bounded cost; display a targeted reconciliation/record-maintenance need rather than truncating evidence. No automatic cleanup is authorized.

Assign each mock response a known synthetic cost; assert exact returned-cost sums separately from request counts. Repeat without cost data and require unknown coverage. Synthetic costs establish no production point ceiling. Record source-fixture before/after counts and costs with fixture/coverage identity. Include actual CLI preflight/hooks and publisher, not only a pure calculator. Fail on unclassified transport. After-fix measurements remain implementation work.
