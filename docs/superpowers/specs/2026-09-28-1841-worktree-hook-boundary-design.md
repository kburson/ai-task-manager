# Worktree-scoped agent access and AITM hook simplification — design specification

- **Issue:** [#1841](https://github.com/kburson/ai-task-manager/issues/1841)
- **Date:** 2026-09-28
- **Status:** Draft for review
- **Source:** #1841 live issue body and its [guard inventory](https://github.com/kburson/ai-task-manager/issues/1841#issuecomment-5873006963); the issue body may evolve during review
- **Baseline:** `92bf48881640a07fa2a19d45f872d7b6c47b4f99` in the isolated #1841 worktree

## Decision sought

Replace AITM's stage-dependent local read/write policy with a checkout boundary and retain narrowly scoped rules for governed remote operations and active artifact review. An agent may read and mutate files within its invoking linked worktree; in the primary checkout, the clone root is the local boundary. `.scratch/**` is ordinary writable space in every task state, including no bound issue.

This document specifies the desired AITM behavior and migration. It does not claim that a regular expression over a Bash command can confine an arbitrary process. Actual process-level filesystem confinement belongs to the host sandbox. AITM must report whether that confinement is configured and must not label a host as bounded when it is not.

## Evidence and problem

The installed baseline at `72563c04` wires `bash-guard.mjs`, `activity-guard.mjs`, and `source-edit-gate.mjs` into Codex and Claude PreToolUse. This worktree temporarily omits those registrations, as recorded under Migration sequence. The Bash guard mixes path scanning, fleet binding, GitHub command restrictions, and commit attribution. The activity guard currently classifies commands and files against an eight-state tool-permission matrix; that matrix is not the desired definition of the eight lifecycle stages. The source gate repeats state, assignee, and deep-dive checks. Either hook can refuse a legitimate local action.

Three observed failures establish the need for change:

1. Two independent binding defects exist. `bash-guard.mjs:146` omits the hook payload's `session_id`, so the environment-derived session can differ from the invoking agent. Independently, `resolveCurrentSessionWorktreeBinding` seeds candidates from the fleet and selects the newest surviving record (`worktree-binding-guard.mjs:156-163,193`), even when the session id is correct. The latter mechanism selected #1837's child-worktree record and refused the fresh #1841 checkout; passing the payload id alone cannot repair it. #1837 is now closed; its path is a regression fixture, not an excluded codebase.
2. Bash creation under `.scratch/gh` classifies as `WRITE_OTHER` and a Markdown input under it as `WRITE_DOCS`. Backlog refuses both, while the file-tool hooks exempt scratch. The hook thus blocks the very governed issue-body draft AITM asks an agent to create.
3. Codex `apply_patch` supplies text in `tool_input.command`, whereas `extractApplyPatchText` accepts only `patch`, `input`, or `text`. The resulting parser refusal blocks an ordinary in-root patch.

Command-string guards are also bypassable by invoking an equivalent child process through a wrapper. Both `bash-guard.mjs` and `activity-policy.mjs` maintain separate `stripQuotedRegions` heuristics with false-positive rationale; escaped or unbalanced quotes can desynchronize either mask. They are useful for catching accidental direct GitHub commands, not as a security boundary for filesystem effects.

## Approaches considered

1. **Keep current guards and add exceptions.** This retains the stage matrix and overlapping shell decisions. Rejected because each tool or scratch case needs another exception.
2. **Delete every guard.** This restores local access but removes explicit file-target containment and raw GitHub mutation warnings. Rejected because these narrow checks serve the stated checkout and issue-integrity boundaries.
3. **Use a checkout boundary plus operation-level governance.** Local file targets use the invoking root, the host confines shell effects, and AITM verbs validate issue and evidence transitions. Selected because ordinary local work no longer depends on lifecycle state.

## Scope and ownership

AITM owns task/session binding, its installed hook registrations, issue/board/body/close operations, and transition evidence. The standalone `ai-peer-review` package owns the active review protocol. The installed `.codex/skills/peer-review/SKILL.md` currently forbids reviewer Git commands and writes outside the response and package scratch, and seals the index and entire worktree. That is broader than the maintainer's requested rule that only the author may mutate the authoritative spec or plan during active partner review. #1841 must track a dependent `ai-peer-review` change, verify its generated provider policies and installed behavior, and cannot pass the review-ownership criterion merely by linking an unresolved issue.

The host owns process-level isolation. For Codex, use the workspace-write root supplied by the host. For Claude or another provider, validate an equivalent host or OS sandbox when available. If there is no reliable sandbox, AITM must say "filesystem boundary not verified" in setup/doctor output and must not claim that its Bash hook enforces one. Lack of a sandbox is surfaced as a capability limitation, not silently replaced with the current brittle command scanner. Host authorization governs outside-root working-file writes and the narrow Git administrative access described below.

## Proposed architecture

### 1. Exact session and checkout resolution

For a hook invocation, use the payload `session_id` and effective invocation directory in that order: tool `workdir`/`cwd` when supplied, then hook `cwd`, then process cwd. For direct Git commands with a directory selector, resolve its target before selecting the checkout. Canonicalize the selected directory to the containing Git worktree root; a `.git` file identifies a linked worktree, and a `.git` directory identifies the primary clone.

Read only that root's active record for the exact session. Do not search the fleet for a newer binding. `AI_TASK_MANAGER_PROJECT_DIR` and `TASK_TRACKER_PROJECT_DIR` do not seed alternative checkout candidates for hook resolution; an override may describe the invoking root only when its canonical path equals the root selected from the effective invocation directory. Mismatch is reported for governed operations and never redirects local work. If this root has no record, local file work is still allowed. A local edit, test, build, or Git operation inside a checkout authorized by the host is not refused merely because another checkout has an issue binding. A governed AITM mutation must independently establish its target issue, branch, live session, and target worktree; a mismatch with a genuinely foreign binding is refused with both identities. An explicit audited foreign-worktree override may authorize only the governed mutation it names, and failed or unavailable audit persistence must refuse the override. For `git -C <child>`, resolve the child as the effective checkout; host access to that checkout is still required, and any governed AITM verb targeting it must match its binding. Stop, pause, closed-binding release, and resume must not leave an occupancy claim that blocks a later valid session.

### 2. Local file boundary

Retain a small PreToolUse boundary for file tools whose targets are explicit: Edit, Write, NotebookEdit, and Codex apply_patch. Resolve every target lexically and physically against the invoking worktree root, including existing symlink ancestors and nonexistent final paths. A multi-target operation is allowed only when every target is inside the same permitted root. An outside target is handed to the host's approval boundary or refused according to the provider contract. Path parsing must accept the actual payload shapes from both providers and refuse an ambiguous target list without partially applying a patch. For Codex `apply_patch`, accept `tool_input.command` when it is a string containing the patch text. Treat `command`, `patch`, `input`, and `text` as equivalent payload fields: if more than one nonempty field is present, every value must be an identical string under the existing conflict rule; none takes precedence. Reject arrays and other non-string command shapes until a captured provider payload establishes a safe contract for them. Preserve `safePatchPath`'s existing rejection of backslashes and `.`/`..` segments before containment checks, and add atomic containment checks for every parsed target.

No AITM file classification, issue state, owner, deep-dive marker, or network lookup runs for a contained local file write. `.scratch/**` has no special permission gate because it is inside the checkout. Delete the current file-tool-only scratch/tmp carve-out (`activity-guard.mjs:167-177`) when removing the Bash activity classifier; do not add a new special case. `.tmp/**` and other contained files receive the same local access rule. Reads are governed by host permissions; AITM removes its custom read allowlist.

Bash cannot be confined through static command parsing. Remove AITM's generic read/write target regexes and activity classification from the Bash PreToolUse path. Validate process-level confinement with a provider-specific integration fixture; report the capability in doctor/setup. A host that cannot enforce the boundary is accurately described as unverified rather than being represented as protected by regexes.

Linked-worktree Git administration is distinct from working-file access. The checkout's `.git` file points to a per-worktree Git directory, while the common Git directory contains shared objects, refs, and logs; both may be outside the checkout root. Discover these paths from Git's resolved metadata for the selected repository. Host permissions govern ordinary `git add` and `git commit` metadata writes; AITM must neither refuse them for lack of an expressible VCS capability nor declare a working operation broken. Where the host requires per-operation authorization, use that host path; where it cannot report capability, label Git metadata access unverified and test the actual operation. Do not grant agent file tools, arbitrary shell writes, or sibling/primary working files a general exception for those external paths. If an attempted Git operation is denied by the host, report the observed denial and its host approval path rather than attributing it to AITM. Integration tests must complete add and commit in a linked worktree under the claimed host capability, while refusing unauthorized writes to primary or sibling working files.

### 3. Governed operations and evidence

Preserve validation inside AITM's issue creation, issue-body mutation, board transition, approval, close, and protected evidence APIs. A local source edit, test, build, or commit may happen at any issue state; the agent cannot claim Develop/Test/Review/Done without passing the stage and evidence gates in force at transition time. Their future requirements belong to the lifecycle stories above. Exact issue/assignee checks belong to governed publication and evidence attribution, not every local edit or commit. Remove `checkCommitAssigneeLock` from Bash PreToolUse; retain commit-subject format lint without network ownership lookup. At `commit-trace`, review preflight, and close, validate each claimed `[#N]` commit against the target issue, its single owner, and the live attribution evidence before accepting it as a deliverable. A failed or unavailable owner lookup blocks only that governed evidence claim, never the local commit. A network outage cannot freeze local drafting or tests.

Separate the direct-command GitHub guard from filesystem policy. It may refuse obvious raw issue creation, issue-body replacement, close, protected-comment mutation, and unauthorized Project mutation to prevent accidental bypass. Read-only GitHub and board inspection must pass. This hook is an advisory accident barrier: it cannot secure an unrestricted shell or token. The canonical AITM mutation API remains the authority.

The installed-copy self-edit ban and the source-edit chore bypass become unnecessary local access rules. AITM's own source checkout, including its `node_modules/ai-task-manager -> ..` self-link, must remain editable inside the worktree. Installer and documentation references to removed guards must be updated so a fresh install does not resurrect them.

### 4. Review artifact ownership

During an active `ai-peer-review` session, only the registered author may mutate, stage, commit, or push the authoritative spec or plan. The reviewer may read it and mutate unrelated files, including `.scratch/**`, within the reviewer checkout's host boundary. The installed peer-review skill and provider launch policy currently impose a reviewer-wide Git/write seal, so AITM hook removal alone cannot deliver this contract. The owning package must revise its authoritative protocol, generated skill text, provider permissions, and runtime enforcement; AITM must adopt the resulting version and verify it. Tests must refuse reviewer mutation of the authoritative artifact, allow reviewer writes to unrelated contained files and scratch, and prove that the artifact-only restriction ends after review. A dependent issue is tracking, not acceptance evidence. Until the owning-package behavior is implemented and verified, #1841's review-ownership criterion remains unmet.

## Risks and limits

- AITM cannot infer every Bash side effect from text. The design intentionally stops claiming that its regexes enforce a filesystem sandbox.
- Provider sandboxes differ. Capability reporting must be explicit, and tests must distinguish "host denied" from "AITM hook denied."
- Removing a PreToolUse stage gate may expose tools during Backlog or Review, but evidence gates still control what the issue can claim. Tests must show both sides of that contract.
- Raw GitHub commands can be wrapped by a shell or another process. The remote-command hook catches common mistakes; it is not token-level access control.
- AC7–AC13 currently cite one focused verification command (`vc:7`); it must gain each mapped case during implementation. A passing old test without those cases is not acceptance evidence.

## Non-goals

This work does not alter #1837's completed GraphQL feature, grant unapproved writes outside the checkout, waive issue transition evidence, or move the independent peer-review protocol into AITM. It does not make an unconfined host process safe by renaming a hook.
