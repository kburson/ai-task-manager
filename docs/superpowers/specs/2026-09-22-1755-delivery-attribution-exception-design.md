# Scoped delivery attribution exception

Date: 2026-09-22. Issue: #1755. Status: approved architecture; implementation design.

## Problem and boundary

AITM rejects mixed attributed and unattributed PR source history with `delivery-preflight:attribution predicate=source-attribution-conflict`. Rewriting accepted history destroys exact-head Test, Review, CI, and audit evidence. This predicate is in delivery preflight, not the `delivery.commit-provenance` requirement in `aitm.workflow-exception/v1`; that requirement governs lifecycle transition-commit provenance. The generic workflow-exception catalog and its prohibition on provenance waivers remain unchanged. This feature adds a separate, default-closed exception for one open PR source history and one delivery intent operation. It does not activate an exception for ai-peer-review #39.

The exception is deliberately outside `aitm.workflow-policy/v1`. `workflow-preflight` and its policy snapshot continue to evaluate catalog requirements and do not report this delivery-specific exception as a satisfied or waived requirement. They are not delivery authorization. The new `delivery-attribution-exception show #N` command, delivery preflight, pending intent, and final receipt expose its state and scope; the operator guide must state this distinction. A malformed or conflicting exception record is a delivery blocker, never a normal attribution pass.

## Authority and operator sequence

`aitm delivery-attribution-exception prepare #N` reads the issue, PR, and complete paginated GitHub PR source commits. It displays the raw inventory digest, the post-classification commits needing mappings, and a request template. This inspection is read-only. Recording authority for #1755 is **Codex-only**: the existing `aitm.authorization-source/v1` validator accepts `codex-session/v1`, the loader reads Codex rollout user messages, and the stored authority requires `codex-session-transcript`. A second host adapter is out of scope. On a non-Codex host, `prepare` reports `authorization-host-unsupported` and does not issue an authorization statement template; `record` refuses the same host. The read-only `show` command may run on other hosts.

The first template contains generated exception and operation IDs. The operator fills it with an explicit positive issue number for each excepted SHA and a canonical expiry, then reruns `prepare #N --input-file <path>`. This second preparation validates the complete candidate, including those immutable IDs, exact scope, mappings, expiry, and a conservative upper bound on rendered comment size, and prints the canonical proposal digest and exact user statement. The first, unfilled template has no authorizing digest. The user sends that exact statement through a supported Codex host user message. Its quoted proposal digest binds the filled request, not merely the PR head.

`record #N --input-file <path>` resolves the user message through `createCodexSessionSourceLoader` and `resolveWorkflowExceptionAuthority`, then recomputes the candidate and proposal digest against live PR and issue state. The source loader discards injection-flagged text blocks, trims and joins the remaining `input_text` blocks, and hashes that filtered statement. `source.statementHash` must match this loader-derived statement hash. Separately, the proposal digest embedded in the verified statement must match the freshly computed candidate digest, and the remaining statement must exactly match the printed authorization form. Filtered or missing text that changes the statement fails closed as `authorization-source-mismatch`; an injection-flagged block alone never grants authority. A request file, environment variable, label, ordinary GitHub comment, or agent text alone grants no authority.

The new versioned GitHub comment envelope contains unique exception and operation IDs; exact repository, issue, PR, base/head refs and head SHA; the SHA-256 digest of the complete ordered raw source inventory; only the excepted `(SHA, subject, issue)` entries; sorted resulting attribution tokens; expiry; verified source-message reference; recording actor; and `host-verified-user-message` level. The complete raw inventory is recomputed, not copied into the comment. Before printing an authorizing statement, filled `prepare` computes an upper bound using the candidate plus maximum allowed lengths for the later source reference, statement, actor, and envelope overhead; it refuses a possible body above a conservative 60 KiB UTF-8 limit or an applicable package bound. `record` checks the exact rendered body and live state before append. `revise` appends a superseding revision with fresh user authority; `revoke` appends a revocation. Old records remain audit history. Edited, malformed, conflicting, stale, expired, revoked, or unsupported chains fail closed. Readback after append must prove the exact record; ambiguous transport never implies success.

## Source inventory and delivery evaluation

For an open PR, the complete paginated GitHub PR commit connection is the authoritative raw inventory, in oldest-to-head order. Its canonical digest includes every `(oid, full subject)` pair and the order. The local `origin/trunk..HEAD` range is separately read as `(oid, subject)` pairs, reversed from `git log` order, and reconciled exactly against the GitHub inventory before using an exception. Any missing, extra, reordered, or different SHA or subject fails closed. The preflight input contract and attribution builder gain a SHA-bearing source inventory for the exceptional open-PR path; the ordinary `string[]` subject path retains its current strict behavior. Duplicate subjects on distinct SHAs remain distinguishable.

The existing `classifySourceCommitSubjects` merge exemption runs on the complete GitHub inventory before identifying mapping candidates. Its output must retain `(oid, subject)` pairs and the verified-merge-exempted SHAs, rather than reducing them to title strings. Only post-classification attributable commits are parsed or mapped. A verified merge exempted by that classifier must never have a mapping, though it remains in the raw inventory digest. A merge subject containing `#` is not exempt under the current heuristic and needs a mapping if the strict parser rejects it. An inspection failure leaves the commit attributable and fails closed unless explicitly mapped.

Ordinary delivery keeps the strict subject parser and its refusal. On an attribution failure in the open-PR `validateDeliveryPreflight` path only, the active scoped exception evaluator may supply mappings. It requires exactly one authorized mapping for every post-classification subject rejected by the canonical parser and none for subjects the parser accepts or merges it exempts. It rejects duplicate SHA or mapping, wildcard or nonpositive issue numbers, extra or missing mappings, wrong refs/head/PR/repository/issue, expiration, and competing active records. A well-formed but semantically wrong `[#N]` token is not eligible for this exception; the ordinary parser retains that token verbatim. The top-level issue must appear in the resulting tokens. Commit title and message bytes derive deterministically from parsed canonical tokens plus authorized mappings.

Immediately before emitting a provider merge action, AITM re-reads GitHub PR metadata and the complete source inventory, reruns local/GitHub reconciliation and merge classification, and recomputes the proposal and inventory digests. Drift in head, order, SHA, subject, scope, or mappings invalidates the exception. Existing binding, lifecycle, ownership, dependency, clean-tree, exact-head Test/Review, CI, mergeability, protection, provider-action, trunk reachability, and receipt checks stay in force. The exception applies to this open-PR preflight and verification after its own governed merge. Already-merged external recovery, historical recovery, and historical reconstruction keep their existing `metadataWarnings` behavior and cannot acquire this exception retroactively.

## Intent, retry, and truthful receipt

Ordinary deliveries continue emitting `aitm.delivery-intent/v1` and `aitm.delivery-receipt/v1` or warning-bearing receipt v2; absence of an exception disposition means an ordinary attribution pass. A waived open-PR delivery emits `aitm.delivery-intent/v2` with `attributionDisposition: "waived"`, exception record ID, operation ID, raw source digest, proposal/scope digest, exact mappings, and resulting tokens. Its final receipt uses `aitm.delivery-receipt/v3` with the waived disposition and immutable exception/intent references. Receipt v3 permits independently justified sorted `metadataWarnings`, but must not carry `missing-source-attribution` for the source inventory the exception authorizes. Existing intent v1 and receipt v1/v2 records remain readable; all schemas have exact-key validators.

The two existing `AUTHORIZED_INTENT_KEYS` projections in `delivery-records.mjs` and `deliver.mjs` must be unified or updated together. Retry equivalence includes schema, disposition, exception record ID, operation ID, raw inventory and proposal digests, exact mappings, tokens, and existing commit text fields. A v1 passed intent can never compare equal to a v2 waived intent. A pending v2 intent is reusable only for the same unchanged exception and operation; a new intent cannot consume that authorization. The exception cannot authorize another PR, head, issue, repository, commit set, or operation.

Merge verification compares the live source inventory, authorized intent, actual merge commit attribution, and recorded exception. The visible receipt labels the waiver and cites the verified source-message reference, recording actor, mappings, and intent through its immutable exception record; it never presents the waiver as an ordinary attribution pass.
