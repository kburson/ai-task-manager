## Premise

Money that arrives without earned effort gets spent without earned judgment — the "house money effect" that shows up in gambling, windfall investing, and (per the original pitch) in the folk psychology around prostitution and political money. Agentic AI tooling hands product managers the power to build and rebuild software without the earned cost that used to force restraint — writing the code, staffing engineers, living with schedule pain. Without that earned cost, some managers — intoxicated by newly developing agentic muscles, not fundamentally worse people — default to regenerating rather than hardening whenever the software needs to change. This produces genuinely disposable, ever-shifting codebases instead of one evolving, hardened codebase, directly contradicting the "we don't ship shit" craftsmanship ethos and the series' own Agentic Agile Delivery thesis.

## Core thesis (converged through research + discussion)

The mechanism is not "AI makes code cheap to lose." It's narrower and sharper: **when a manager regenerates a product from an updated spec instead of directing agents to refactor the existing codebase to meet that spec, the code is fully replaced — different language, structure, and patterns are all live possibilities — while only the *product* (features, workflow, UX) actually evolves.** The spec can carry memory forward (Kaizen); the code underneath it, in a full-regeneration cycle, cannot.

Two consequences follow, at two different scales:

1. **Perpetual beta (single-product scale).** Every regeneration cycle resets code maturity to zero. Feature polish and workflow thinking compound cycle over cycle (because that lives in the spec); code stability never compounds, because the product never goes through a hardening phase before the next rebuild. The product can never leave beta, by construction — not because of bad luck, but because the org keeps re-paying the cheap initial-build cost and never pays the expensive, unavoidable maintenance cost. (Maintenance is well-documented as 60-80% of total lifecycle cost — Erlikh 2000, Glass's *Facts and Fallacies of Software Engineering* — a distinct, safe claim from Boehm's contested cost-of-change multipliers, which this article does not cite.)

2. **Frankenstein bolt-ons (enterprise scale).** Large products can't be defined by one spec — a master spec plus sub-specs refine different portions. When a sub-spec is regenerated independently, the new module can be internally well-built (agents aren't sloppy) while being structurally incoherent with the rest of the body — a different style limb grafted onto an existing torso. This is categorically different from the pre-AI "Big Ball of Mud" anti-pattern (Foote & Yoder, 1997): BBoM is organic, continuous decay of one codebase; Frankenstein is discrete incoherence between separately-generated, individually-clean pieces. The failure is at the seams, not inside the parts.

**Resolution:** the fix is not "never regenerate." It's that **stitching becomes a deliberate, governed engineering activity** — before a regenerated sub-spec's code gets bolted on, agents (under real Technical Product Owner oversight, per the series' existing Agentic Agile Delivery model) investigate the surrounding corpus and propose the refactoring needed to integrate the new piece, rather than dropping it in next to the old. This is the same evidence-based-oversight mechanism the series already argues for (articles 05, 09) — applied specifically at integration seams, where regeneration cycles are most likely to introduce incoherence.

## Additional mechanism: why regenerate wins over refactor (captured from live discussion, 2026-08-18)

This section captures a deeper causal chain that emerged through discussion after the initial design was drafted. It sharpens *why* regenerate beats refactor as a choice, beyond "it's cheap and psychologically easy" — and it gives the article a first-party evidence base (AITM's own backlog) instead of leaning entirely on external, thinly-sourced citations.

**The survival-analysis counter-study (agent-authored code is touched less) has at least three competing explanations, not one.** The research file currently frames "touched less" as ownership avoidance — nobody feels responsible for code they didn't really pay for. Two sharper alternatives surfaced in discussion: (1) trust asymmetry — teams may distrust their own judgment against the agent's output more than they distrust the agent's actual error rate, which is abdication dressed as caution; and (2) macroscopic illegibility, microscopic soundness — agent code optimized to satisfy a spec can be locally clean and globally opaque, so touching any thread feels like it could unravel something nobody can see the shape of. Explanation (2) is structural, not psychological, and it's the one worth building the mechanism section around.

**Macroscopic illegibility is what makes refactoring illegible-at-scale code a genuinely worse bet than rebuilding it — which is what makes regenerate the *rational-seeming* choice, not just the easy one.** This sharpens the "power drunk manager" framing: the manager isn't only intoxicated by cheap power, they're also making a locally reasonable bet given the tools in front of them. That bet still compounds into perpetual beta and Frankenstein bolt-ons at scale — but naming it as a reasonable bet rather than a moral failure keeps the diagnosis sympathetic, which the tone notes already require.

**The resolution ("governed stitching") needs a concrete mechanism, and AITM's own backlog behavior supplies one: a well-decomposed backlog functions as a refactoring reference, not just a task queue.** Tasks reference other tasks; completed work gets cited by name when new work touches related territory; code carries comment references back to the backlog item that produced it. This gives a refactoring agent a bounded, walkable graph to scope the blast radius of a change, instead of needing to hold the entire corpus in its head. This directly completes the earlier "control plane with no memory of its own history is amnesia wearing governance's clothes" line — a control plane *with* task-to-task memory isn't just governance, it's a refactoring reference.

**This mechanism is only as trustworthy as the backlog's own decomposition discipline.** A coarse-grained or myopically-scoped task passes its blind spots up the chain the same way a myopic spec passes blind spots down into code. So "governed stitching" doesn't just need *a* backlog — it needs a *well-governed* one (mandatory estimate/size, sub-issue nesting, blocked-by annotations before work starts). Sloppy backlog discipline, and the refactoring-reference mechanism collapses along with the spec.

**Live, first-party evidence from building AITM itself, not literature:** the backlog's documentation is stratified by audience and cost. Design agents read title and story prose first; if that's insufficient, they drill into the task's deep-dive and code references; timing logs and validation evidence are a separate tier that exists purely for human audit and isn't part of the agent's decision path at all. This is progressive-disclosure memory, not an undifferentiated pile of documentation — it's what makes the refactoring-reference mechanism cheap to use instead of requiring an agent to read everything up front. This is a stronger, more specific claim than "the backlog has memory," and it's directly observed in this project rather than argued from theory. Even a single closed task's full trail (synopsis, scope, deep dive, evidentiary comments) aggregates to real depth beyond the immediate task description — which meaningfully strengthens the roadmap claim.

**Hardening has a real, admitted cost, and that cost is the article's sharpest available anchor.** In AITM's own numbers: the automated test suite takes roughly 15 minutes per run, and a task needing several runs during implementation can move from a 30-minute task to a 3-hour one. That is the literal price of not being in perpetual beta — and it's exactly the price a manager flush with cheap-regeneration confidence is tempted to skip. This is better than any literature citation for the article's cost-economics beat: it's lived, it's first-party, and it's honest about the cost side rather than only selling the benefit.

**Scope flag: AITM itself may deserve its own article (or more than one), separate from this one.** The depth of AITM's own auditable specification trail — spec → plan → epics → stories → JIT deep-dive analysis → evolving automated test bed — is substantial enough to warrant a dedicated feature/benefits piece. This design does not attempt to absorb that scope. If AITM's own governed-backlog behavior is used here, it should appear as a first-party case-study aside supporting the resolution, not as the article's main subject; the dedicated AITM piece is a distinct, separately-designed article, likely positioned as the positive counter-example to this one's cautionary case.

## Additional mechanism: the seasoned manager's fork, and why the piece needs both sides (captured from live discussion, 2026-08-18)

The draft so far is built almost entirely around one character: the manager who is new to agentic tooling (or running a new product with no scar tissue) and defaults to reckless regeneration because nothing in the moment tells them not to. That character is real and well-supported, but writing only that character makes the piece one-sided — diagnosis with a prescription bolted on at the end, not a genuine duality. The user's framing: "the yin without the yang is just a colored dot." The fix is structural, not cosmetic — the disciplined manager needs to be a fully realized character running in parallel through the piece, not a moral appended in the resolution paragraph.

**A seasoned manager on an existing product faces the same windfall with actual judgment already in place, and that produces a genuine fork, not a foregone conclusion.** The house money effect doesn't erase judgment — it tests it against a much cheaper temptation than the manager has ever faced before. This reframes the thesis away from "agentic AI causes reckless behavior" and toward "agentic AI amplifies whatever judgment is already there — it makes good judgment cheaper to execute and bad judgment cheaper to indulge." That is a stronger, less deterministic claim than the current draft carries, and it is the version worth writing.

**Three concrete branches for the seasoned manager, not equally likely or equally bad:**

1. **Bolt-on everywhere.** The naive manager's failure mode transplanted onto someone who should know better. Same Frankenstein mechanism already in the design, but now motivated by "it's so cheap, why not" instead of genuine confusion about the old architecture. A seasoned manager has less excuse here — they understand the system, they're just not paying the discipline tax because nothing forces them to.
2. **Iterative hardening.** The seasoned manager directs agents to inspect, clean, and harden the existing corpus — spending the same cheap agentic labor on debt paydown instead of feature sprawl. This is the article's resolution (governed stitching) made into an active choice a character makes, not a passive best-practice description. The house money effect predicts reckless spending; it doesn't require it. Some people bank the windfall.
3. **Targeted wholesale replacement of a known-bad subsystem.** The most interesting branch, because it is not the villain case — it's arguably the correct, judgment-driven use of the regenerate option. A manager who chooses to regenerate one specific subsystem that has been a chronic, well-understood pain point, informed by years of scar tissue about exactly where and why it breaks, is doing scoped regeneration against known history — the opposite of the naive manager's whole-product panic-rebuild. This turns "regenerate vs. refactor" from a binary into a spectrum with a judgment variable: undisciplined regeneration is the failure mode; bounded, history-informed regeneration is the power used well.

**Structural implication for drafting:** the piece should run the naive-manager and seasoned-manager cases in parallel through the middle acts — same mechanism (regenerate vs. refactor), same tool, different judgment, different outcome — rather than spending three acts on the cautionary case and reserving the disciplined case for a closing prescription. Branch 3 in particular deserves real page space: it's the clearest demonstration that the article's target is undisciplined use of a new power, not the power or the act of regeneration itself. This likely reshapes Act 3 ("two scales of consequence") and Act 4 ("the Agentic Agile Delivery answer") into a single act that runs both outcomes of the same fork side by side, rather than treating consequence and resolution as sequential.

## Structure (three acts, thesis-first)

Matches the series' existing analytical-essay voice (articles 04, 09) — concept-first, not narrative-first — per the earlier structural discussion.

1. **Hook + analogy.** Open on the "easy come, easy go" phrase and the house money effect (Thaler & Johnson, 1990) as a legitimate academic anchor, then the "power drunk manager with newly developing muscles" image — not a moral failing, an immature-skill problem, which is what makes the resolution optimistic rather than cynical. Ground it with one concrete case (Willison's April 2026 essay on discarding a working AI-built prototype) before generalizing.
2. **The mechanism.** Regenerate vs. refactor as the actual fork in the road. Distinguish spec evolution (can carry memory, is often genuinely good — better UX, better feature balance) from code evolution (does not automatically follow from spec evolution in a full-regeneration pattern). Introduce the maintenance-cost economics here: regeneration defers the expensive phase, it doesn't eliminate it.
3. **The fork, run in parallel — not sequential consequence-then-resolution.** Per the seasoned-manager discussion above, this act should not spend its full length on the cautionary case before pivoting to a prescription. Instead it runs the same mechanism (regenerate vs. refactor) through two characters at once: the naive/new manager sliding into perpetual beta and Frankenstein bolt-ons, and the seasoned manager's three branches (bolt-on-everywhere as the same failure transplanted onto someone who should know better; iterative hardening as the windfall banked instead of spent; targeted wholesale replacement of a known-bad subsystem as regeneration used well — bounded, history-informed, judgment-driven). Perpetual beta and Frankenstein bolt-ons remain the consequence side of the naive case (contrast Frankenstein explicitly with Big Ball of Mud — discrete incoherence between clean parts vs. organic decay of one mass). Branch 3 gets real space here as the clearest proof the target is undisciplined use, not regeneration itself.
4. **The Agentic Agile Delivery answer.** Governed stitching as a concrete practice, not a platitude — corpus-aware refactoring proposals as a first-class, evidenced step at every regeneration/integration boundary, and the throughline connecting it to branches 2 and 3 above: judgment about when to regenerate and when to refactor is exactly what Technical Product Owner oversight is for. Land on Beck & Fowler's "cognitive debt" framing (Thoughtworks Deer Valley retreat, Feb 2026) as the resolution anchor: craftsmanship discipline is the precondition for effective AI collaboration, not an obsolete luxury.

## Citations: use, correct, or avoid

Full detail in the research file; summary for drafting discipline:

- **Use as-is:** Thaler & Johnson (1990) house money effect; Foote & Yoder (1997) Big Ball of Mud; Erlikh (2000) / Glass maintenance-cost-share literature; GitClear 2026 Maintainability Gap report; Beck & Fowler cognitive-debt framing; Willison's April 2026 essay.
- **Use only in corrected form:** Uncle Bob Martin's "we don't ship shit" — present as the historical craftsmanship stance being tested, not as his current unqualified position (he has reportedly stepped back from line-by-line AI code review in 2025-2026). Do not imply he still holds the line unchanged.
- **Do not cite as fact:** Boehm's cost-of-change curve multipliers (1x/6.5x/15x/100x) — flagged as likely-fabricated folklore by Bossavit. Brooks' "build one to throw away" — he retracted this himself in 1995; do not use as clean precedent for planned disposal.
- **Note but do not lean on:** the 932K-PR survival-analysis study (AI code modified less often). Established in discussion that this measures a different phenomenon (human ownership-avoidance in mixed codebases) than this article's core mechanism (wholesale regeneration with no human code-layer decision at all). May get a single-sentence mention as a related-but-distinct pattern; should not be treated as primary evidence for this article's claim.
- **Verify before drafting:** exact citations for the survival study, the Beck/Fowler retreat reporting, and Uncle Bob's 2025-2026 pivot were gathered by research agents without fully pinned URLs. Pin sources before they appear in published prose.
- **First-party case study, use as-is:** AITM's own backlog behavior — task-to-task cross-references, code comments citing backlog item numbers, stratified/progressive-disclosure documentation (title/prose → deep-dive/code refs → human-only evidentiary tier), and the admitted hardening cost (roughly 15 minutes per test run, sometimes pushing a 30-minute task to 3 hours). This is directly observed by the author building this project, not sourced from literature — presented as first-party evidence, not as a generalized industry claim.
