# #1861 explicit empty runtime reassessment

Status: proposed architectural amendment, revised for manual review r2; not approved or implemented. Document consensus, design/Plan approval, candidate verification, deployment and live activation remain separate gates. This records unmet C1 acceptance, not completion of #1861.

## Intent and accepted boundary

A fresh installation without legacy runtime needs an explicit registered route to create an empty valid main store. After proven total loss, an operator needs the same route without inherited grants, followed by reconciliation of canonical GitHub/native-host evidence. Parent R2/R3 requires both outcomes; the accepted decomposition limits empty initialization to proven total absence of legacy/durable data. Ordinary commands never initialize implicitly.

The linked initializer refuses main, requires an activated migration generation and rejects its original roots (`runtime-initialize.mjs:59–83`). Migration planning returns `canonical-reconciliation-required` with no sources (`runtime-migration-plan.mjs:274`). The kernel design's earlier sentence that proven-empty initialization was an existing admitted case is unsupported. This proposal corrects that factual assertion; historical accepted bytes/digests remain preserved, and neither that sentence nor this proposal proves implemented behavior.

Three scenarios have distinct dispositions:

1. Fresh main with complete absence: admit only an exact approved empty plan and a quiescent, unchanged all-root census.
2. Proven total absence after activation: use the same absence policy and fixed records. Operation IDs/physical identities remain plan-specific; serialized plans need not be identical.
3. Surviving legacy bytes, durable residue, partial loss or uncertainty: refuse and preserve exact blockers. Lost durable stores with retained inert legacy originals fall here. This amendment authorizes neither stale-grant re-import, abandonment nor moving originals aside. Existing registered recovery or restoration of an exact known durable backup/proof is the supported recovery disposition; without sufficient evidence, preserve the refusal pending a separately reviewed operator decision. This proposal does not solve selective durable loss with surviving legacy. `abandon-legacy-no-import` would change the accepted total-absence contract and requires separate explicit approval.

## Alternatives and smaller solution

A. Use a distinct protected empty proof, shared migration census machinery and main-only publication. Linked roots then initialize explicitly against the real empty activation proof. Recommended: no synthetic migration inputs or multi-root empty transaction.

B. Extend migration with synthetic sources and an empty-source policy. This conflates trusted observed source bytes with generated records and broadens migration-plan compatibility. Reuse validation/publication primitives without inventing legacy provenance.

C. Defer the capability and retain typed refusal. Honest, but fresh-main/total-loss acceptance and joint release remain incomplete.

Census still covers every registered root. Publish only main's local state `{}`, queue `[]`, shared fleet `{}` and occupancy `{}`, with one control and journal. Empty activation's `originalRoots` is `[mainRoot]`. All other roots receive no writes and require explicit linked initialization, including roots registered before the empty plan. Census membership/active main grants no local authority. Readers must distinguish supported uninitialized roots from loss of original/previously initialized roots; the current missing-control branch needs this distinction and is not claimed to implement it already.

## Shared absence observation and approval

Extract read-only `observeRuntimeAuthorityCensus({ projectRoot, mainRoot, adapters })` from migration's inventory/root/schema/writer machinery. Both planners consume one observation with separate policies. A migration plan blocked only by `canonical-reconciliation-required` is not sufficient empty approval: current destination checks cover only `control.json`/`store/`, and the legacy allowlist skips the durable subtree.

Empty planning requires the entire `<root>/.ai-task-manager/runtime/` prefix absent in every registered root, including an existing empty directory. Thus present/future journal, recovery, batch, staging and coordinator namespaces cannot escape the rule. Also inventory `.db/aitm`, `.tmp/aitm`, supported `.ai-task-manager`/`.claude` authority families and catalog-declared supported authority locations. Configuration/documentation are outside authority inventory. Any authority bytes, lock, malformed/unknown record, alias, unavailable/unadmittable root or incomplete writer/claim observation blocks. Shared extraction must preserve migration's protected-history/retry semantics and approved v1 digests; changed migration digest semantics require explicit versioning.

The canonical observation projection binds sorted registered/unavailable root sets, physical `projectRoot`/`gitDir`/`commonDir`, each authority location's absence or exact protected entry identity/digest, census completeness/unknowns and foreign writers/claims with their identities. Diagnostic timestamps and the invoker's process PID/token are not stable approval fields; retain their genuine observations outside that projection. The sole invoker exception must be proved against the executing registered bootstrap and genuine provider/session/process/host identity. No caller-selected PID or arbitrary removal of writers/claims. A planning process's existing claim does not become the applying process's authority. Unknown identity blocks.

Apply authenticates its current owner, acquires the same protected main-owner coordinator used by migration/batches, then re-observes the complete census under exclusion. Only its exactly proved coordinator artifact and necessary operation-created ancestor directories are exempt from the original-absence comparison. No old journal, unrelated pending artifact, lease or legacy-image process is exempt. The approved projection must match before store/control publication. The shared process census also blocks older writers that ignore leases; a lease alone is not quiescence. Detectable later drift stops publication and preserves the journal.

## Versioned candidate interfaces

Proposed APIs:

- `planEmptyRuntimeInitialization({ projectRoot, mainRoot, adapters })`: asynchronous read-only planner; returns `aitm.runtime-empty-plan/v1`, binding an operation UUID, canonical census observation/digest, main physical identity, fixed records and exact plan digest. Apply re-observes the sealed observation; it does not generate a different UUID and compare complete fresh plans.
- `applyEmptyRuntimeInitialization({ plan, approvedPlanDigest, adapters })`: asynchronous exact-approved publication under a genuine current owner.
- `inspectEmptyRuntimeInitialization({ projectRoot, mainRoot, operationId })`: synchronous filesystem/physical-root observation; returns validated protected state, owner history and exact observed digest. No writes, ownership acquisition, death sampling or ordinary authority reads. Test injection remains internal and cannot provide a production filesystem/root bypass.
- `resumeEmptyRuntimeInitialization({ projectRoot, mainRoot, operationId, observedDigest, approvedPlanDigest, adapters })`: asynchronous exact recovery of original approved payloads under genuine ownership or confirmed exact-owner death.
- `readRuntimeActivationRoot({ projectRoot, mainRoot })`: synchronous read-only main activation validation. Result: `aitm.runtime-activation-observation/v1` with `mainRoot`, `activation: { kind, id, digest }`, `originalRoots`, and `originalRootIdentities: [{ projectRoot, gitDir, commonDir }]`. This validates main's complete protected proof, not the caller's local admission. `kind` is `migration` or `empty-initialization`; `id`/`digest` bind the real migration transaction/approved plan or empty operation/approved plan. No synthetic manifest.

Reuse `INITIAL_RUNTIME_RECORDS` for local bytes; a sibling constant defines shared `fleet/task-fleet.json: '{}\n'` and `fleet/occupancy.json: '{}\n'`. Every fixed byte string passes existing catalog validators. No caller-selected targets/payloads. Publication creates no binding, timer history, gate approval, occupancy, claim or delivery authority.

Main journal: `aitm.runtime-empty-initialization/v1`, at `<main>/.ai-task-manager/runtime/empty-initializations/<operationId>/journal.json`. It captures the complete approved plan, absence, generated bytes, physical identities, genuine owner/history and prepared/publishing/complete status.

Control v2 (main and linked) requires `schema: aitm.runtime-control/v2`, `status`, `projectRoot`, `mainRoot` and `activation: { kind, id, digest }`. Main requires `projectRoot === mainRoot` and forbids `initialization`. A separately initialized linked root requires `projectRoot !== mainRoot` and `initialization: { id, operationId, digest }`, matching its exact protected root journal and approved linked plan. Closed validators reject missing, extra, contradictory or unsupported fields/combinations. Migration-bound controls continue using v1; this proposal emits v2 only for empty activation and its linked roots.

An empty main cannot feed migration-bound linked v1. Linked initialization under empty therefore uses `aitm.runtime-initialization-plan/v2`, `aitm.runtime-initialization/v2` and local control v2. The plan retains the physical linked identity, deterministic root initialization ID, fixed local records and source policy, adds an operation UUID and binds main's real `activation`. Its protected journal carries that plan, exact owner/history and prepared/complete state at `<main>/.ai-task-manager/runtime/initializations/<runtimeInitializationId(projectRoot)>.json`, the same root-keyed location as v1. `runtimeInitializationId` is SHA-256 of the canonical physical project-root path. The operation UUID is inside the journal plan, not the filename. Linked-v2 status/resume derives this path from the invoking registered physical root; resume validates the requested UUID against that journal, plus observed/approved digests and physical identities. It never searches for an operation to select another root, replaces history or trusts a caller path. Readers/recovery bind the main proof and exact linked journal/operation without reading a nonexistent migration manifest. Linked initialization against migration continues using v1, preserving existing arguments and historical plans/journals/controls.

For a linked root missing local control, first validate main activation through the main-only observation. Absent/incomplete/invalid main retains the existing main-state refusal (`RUNTIME_MIGRATION_REQUIRED` for pristine absence, `RUNTIME_TRANSACTION_INCOMPLETE` for unfinished publication, `RUNTIME_CONTROL_INVALID` for missing/corrupt protected proof or partial loss). With active valid main, inspect `originalRoots` and the exact protected root-keyed journal path across v1/v2. A nonoriginal root with no history and no local runtime residue returns `RUNTIME_INITIALIZATION_REQUIRED`, directing explicit registered linked initialization. Membership in `originalRoots` or any protected per-root history returns the existing `RUNTIME_CONTROL_INVALID` partial-loss refusal and directs status/exact recovery or restoration, even if the retained journal is prepared. Status exposes unfinished operations for resume; ordinary reads never reinterpret them as fresh. Local residue, unreadable/malformed history, aliases or uncertain history also refuse; they never count as absence.

Documented limitation: once a linked path is protected by `originalRoots` or per-root history, removing/recreating a linked worktree at the same canonical path still cannot initialize afresh, even with a different `gitDir` or a verified C3 retirement receipt. Fresh initialize-plan/apply returns `RUNTIME_CONTROL_INVALID` with the protected-history reason and journal path. C3 retirement does not erase this history or grant reuse. Supported dispositions are exact restoration/recovery of the original identity where proof permits, or separately admitted creation/registration at a genuinely unused path followed by explicit initialization. Reuse of the old path needs a future approved history/retirement contract; never delete/move the journal, prune or claim a retirement receipt as a bypass. C4 documents this limitation and these dispositions.

Proposed registered grammar:

- `migrate-runtime initialize-plan`: main returns the empty plan; linked returns migration-v1 or empty-v2. Descriptor/handler expose the explicit union.
- `migrate-runtime initialize-apply --plan-file <file> --approved-plan sha256:<digest>`: exact schema/digest and invoking physical root determine dispatch.
- `migrate-runtime status`: expose empty/linked protected journal identities, states and exact observation digests before ordinary authority reads.
- `migrate-runtime initialize-resume --operation <UUID> --observed sha256:<digest> --approved-plan sha256:<digest>`: required for main empty and linked-v2 recovery; reject unrelated extra arguments. Linked v1 retains its existing approved-plan-only route.

Parser, descriptor/help, bootstrap classifier and physical handler agree. No payload, PID, environment override or arbitrary path grants authority.

## Publication, read admission and recovery

After coordinator acquisition and matching all-root observation, publish/fsync the complete exclusive journal before store/control changes. Stage/verify four fixed records on main's destination filesystem; publish a prepared control, rename the store, verify every member, complete/fsync the journal, then publish/fsync active control. Ordinary v2 reads require active matching control AND complete validated activation journal, required records and existing batch admission. Either missing condition refuses. Linked v2 uses the same journal-complete-before-active-control order; historical v1 remains supported.

Status/resume remains bootstrap-reachable. Recover a retained dead coordinator through its exact observed route before resume. Validate observed digest, approved plan, physical identities and participating-root census before writes. Each main destination must be original absence or the protected exact staged/published outcome; nonpublished linked roots retain recorded absence. Conflicting bytes, aliases, uncertain owners, new/missing roots and unbound artifacts refuse without deleting evidence. Resume proves original genuine ownership or exact prior-owner death; owner history records each genuine resumer. Competing/killed recovery follows the same rules.

Operation-created ancestor exceptions are derivable only from the fixed main layout: `runtime/`, `runtime/migrations/` for the shared coordinator, `runtime/empty-initializations/` and `runtime/empty-initializations/<operationId>/`, relative to main's `.ai-task-manager/`. The approved census proves these did not preexist. The first fully written journal records that fixed set and its observed physical directory identities; recovery validates the retained journal, identities and coordinator proof before treating those ancestors as operation-created. This is not a caller allowlist and exempts no sibling entries. Later staging directories derive from the fixed record layout and are recorded/validated with their exact staged outcomes. A crash before a valid first journal leaves protected unbound artifacts refused, including otherwise matching empty ancestors; their names alone never prove ownership.

Pending transitions require original payloads and a validated protected predecessor. No store/control publication precedes a valid first journal. Incomplete/unbound initial artifacts remain typed protected refusals, never guessed or erased; sufficient exact evidence permits original completion. Completed retry validates receipts/read admission without rewriting fixed records, replacing later legitimate state or undoing a proven successor. Post-completion census evolution follows normal linked/successor rules instead of replaying original absence.

Typed outcomes: `RUNTIME_EMPTY_INIT_REFUSED` with protected blocker list; `RUNTIME_INITIALIZATION_REQUIRED` for a proved fresh uninitialized linked root; `RUNTIME_MIGRATION_APPROVAL_REQUIRED` for mismatched/missing approval; `RUNTIME_MIGRATION_PLAN_CHANGED` for prepublication drift; `RUNTIME_MIGRATION_CONFLICT` for conflicting recovery evidence; `RUNTIME_TRANSACTION_INCOMPLETE` for unfinished publication; `RUNTIME_CONTROL_INVALID` for malformed proofs, partial loss or protected-root-history refusal. Existing unknown-writer, busy and unconfirmed-owner meanings remain. Refusals identify the root/artifact and supported inspection/recovery or exact package/backup restoration. Unavailable roots need operator investigation/restoration or separately admitted retirement; never automatic pruning of protected managed worktrees.
